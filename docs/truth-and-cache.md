# 진실과 캐시 — 점과 평면의 표현

> **설계 중, 미구현.** 도달하려는 타입만 적는다.

```
Rat → f64        캐시를 만든다
Rat → BigFloat   판정을 위해 정밀도를 올린다
f64 → 정확        없다
```

아레나는 append-only 이므로 **진실만 들어간다.** 캐시는 곁표에 두어 언제든 버리고 재생한다.

---

## 기반 타입 (이미 있는 것)

```rust
// nacre-scalar — 진실 쪽
pub struct Rat(Ratio<i128>);              // 정확한 유리수, checked 산술
pub struct Angle(Rat);                    // 유리수 degree, 0 <= inner < 360 (정확 mod-360)
pub enum Axis { X, Y, Z }
pub struct Mag(…);                        // 양의 크기, 확장 지수 — 아래 「수치 층」

// nacre-math — 캐시 쪽
pub struct Point<const D: usize> { coords: [f64; D] }
pub type Point3 = Point<3>;
pub type Vector3 = Vector<3>;

// nacre-store — 아레나
pub struct Store<T>  { items: Vec<T> }    // append-only
pub struct Handle<T> { index: u32 }       // 릴리스에서 u32 하나
```

## 점

```rust
/// 정점은 **면들이 만나는 곳**이다 — b-rep 정점의 정의 그대로.
/// 좌표는 진실이 아니라 캐시다.
pub struct Vertex {
    /// 이 점을 **정하는** 세 면. 인접 면이 더 많을 수 있지만(각뿔 꼭대기는 N 개)
    /// 나머지는 **위상이 이미 안다** — 여기 적으면 설명이 둘이 된다.
    pub surfaces: [Handle<Surface>; 3],
}

/// 진실의 f64 실현과 그 실현이 달성한 정확도. 함께 만들어지고 함께 버려진다.
pub struct PointCache {
    pub coord: Point3,
    pub tol: [f64; 3],                        // 축별
}
// 고정밀 실현은 같은 모양의 HpPointCache — 「수치 층」 참조.
```

★★★ **좌표를 진실로 삼는 변종이 없다.** 사용자 치수는 점이 아니라 **평면 계수로** 흘러간다:
프로파일 점을 지나는 두 벽의 계수가 되고, 정점은 `벽1 ∩ 벽2 ∩ 캡` 으로 **파생**된다.

★★ **모션 필드가 없다** — 면들이 자기 모션을 들고 있고, 면이 움직이면 교차점도 정의상 따라 움직인다.
솔리드를 옮길 때 하는 일은 **정의를 새 면 핸들로 다시 가리키는 것**뿐이다.

★ **핸들은 서로 달라야 한다.** 같은 것이 둘이면 교차가 점이 아니라 직선이다 —
평면이 interned 이므로 `s[i] == s[j]` 한 번으로 탐지된다.

### 셋이면 충분하다 — 그리고 정점은 interning 하지 않는다

한 점에 면이 셋보다 많이 모일 수 있다(각뿔 꼭대기는 밑면 변만큼). 그러면 그 점을 정하는
트리플이 여럿이고, *"어느 셋인가"* 를 정해야 할 것처럼 보인다. 그런데 **저장이 풀 문제가 아니다.**

★★★ **정점은 interning 할 수 없다** — 인접 관계가 **자라기** 때문이다:

```
정점 v 의 인접 평면 = {P1, P2, P3}
      ↓ 나중 연산이 v 를 지나는 면을 하나 더 만든다
                    = {P1, P2, P3, P4}       ← ★ 같은 점인데 키가 바뀐다
```

전체 집합으로 키를 잡든 사전순 최소 트리플로 잡든 **똑같이 깨진다**(더 작은 핸들이 나중에 온다).
⇒ 점의 동일성을 **인접으로 키잡을 수 없다.**

★ **그래도 잃는 것이 없다.** *"세 엣지가 한 Vertex 핸들을 공유한다"* 는 이득은 **한 연산 안**에서
필요한 것이고, 배열이 오늘 이미 `Node::Seam([usize;3])` 로 **한 트리플을 일관되게** 써서 얻는다.
연산을 넘는 interning 은 애초에 필요하지 않았다.

★★ 그 대신 **점의 동일성은 기하 질문으로 남는다**: 다른 연산에서 나온 `{P1,P2,P3}` 와
`{P1,P2,P4}` 가 같은 점인지는 술어가 답한다(오늘 `merge_coincident` 가 하는 일).
*"같으면 같은 핸들"* 이 구성 시점에 일어나는 것은 **평면뿐**이다.

★★ 그래서 저장은 **정하는 세 면**만 든다. 나머지 인접 면은 위상이 알고 있으므로,
적으면 **두 번째 설명**이 되고 그것이 이 문서가 내내 피해온 것이다.
같은 이유로 **4-평면 동시성**(한 점을 두 트리플이 가리키는 것)도 저장이 아니라
**한 연산 안의 문제**이고, 배열의 alias 장치가 다루는 자리다.

★ 술어는 셋을 그대로 받는다. 정상적인 정점에서는 인접 평면 어느 셋도 그 점을 정한다:

- **평행한 둘**은 있을 수 없다 — 서로 다른 평행 평면은 만나지 않으므로 둘 다 그 점을 지날 수 없고,
  같은 평면이면 interning 이 이미 하나로 만들었다.
- **한 직선을 공유하는 셋**도 있을 수 없다 — 그러면 쌍별 교선이 전부 그 직선이 되어 세 면이
  **한 모서리를 공유**하게 되고, 그것은 2-manifold 가 아니다.

★★ 그래도 **`D != 0` 을 단언한다.** 논증이 맞아 보여도 검사되지 않는 불변식은 언젠가 깨지고,
깨졌을 때 나오는 것은 조용한 오답이다. `D` 는 동차좌표를 만들 때 어차피 계산되므로 **공짜**다.

### 담체와 경계 — 곡면 집합이 정하는 것은 절반이다

```rust
Edge {
    surfaces: [Handle<Surface>; 2],            // 담체 직선 (두 면의 교차)
    vertices: [Handle<Vertex>; 2],             // ★ 끝점 — 이것이 있어야 모서리가 정해진다
}
EdgeCache { curve: geom::Curve }               // 캐시 — 평가 가능한 담체
```

★★★ 규칙은 이것이다:

> **곡면 집합은 「담체」를 정하고, 경계가 나머지를 정한다.**
>
> | | 곡면 집합이 주는 것 | 나머지 |
> |---|---|---|
> | **정점** | **점** | ★ 없음 — 0차원이라 경계가 없다 |
> | **모서리** | 직선·곡선 | 끝점 둘 |
> | **면** | 평면·곡면 | 경계 루프 |

★★ **정점만 곡면 집합으로 완전히 정해진다.** 그래서 정점만 좌표를 진실에서 버릴 수 있다.

★ `Edge.surfaces` 는 **파생이 아니다.** 두 끝점의 면 집합을 교집합하면 될 것 같지만, 정점은
*"임의의 결정 트리플"* 만 들기 때문에 `{A,C,E} ∩ {A,B,D} = {A}` 처럼 담체를 놓칠 수 있다.

★ 그리고 그 때문에 **모서리와 면은 interning 하지 않는다**: 두 면이 **여러 토막**에서 만날 수 있고
(U 자 교차), 한 평면 위에 **서로 떨어진 면**이 둘일 수 있다(Cut 이 한 면을 쪼갠다).
곡면 집합만으로는 **어느 것인지** 말하지 못한다.

★ 곡선 **캐시**의 종류는 여기서 다 따지지 않는다: 평면∩평면은 직선이라 깔끔하지만
원통∩평면은 원·타원이고, 모양이 **M6 에서 정해진다**(§「남은 것」 5).
담체가 면 둘이라는 것은 그때도 바뀌지 않는다.

★★ 오늘 `Store<Curve>` 가 들고 있던 것은 **진실이 아니라 캐시**였다 —
tess 가 모서리를 샘플링하고 STEP 이 곡선을 써내려면 필요한 형태다.

## 모션

```rust
// nacre-scalar — 내용이 전부 Rat/Angle/Axis 이므로 여기 산다.
// (판정 층도 이것을 그대로 쓴다 — 층마다 같은 타입을 다시 만들지 않는다.)
pub enum Motion {
    Rotate { axis: Axis, point: [Rat; 3], angle: Angle },
    Translate { offset: [Rat; 3] },
    Mirror { axis: Axis, offset: Rat },       // det = −1

    /// ★ 2b. 축 회전 사슬로 도달할 수 없는 프레임 — 옆면 스케치가 이것을 만든다
    /// (프로파일 변 `(1,2)` 의 옆벽은 각이 `atan(1/2)` 라 유리수 degree 가 아니다).
    ///
    /// ★★★★ **법선을 성분이 아니라 이름으로 든다.** `plane` 의 법선이 곧 이 프레임의 `w` 이고,
    /// `origin`·`ref_dir` 는 **그 평면 자신의 프레임 안**에서 유리수다. 그래서 옆벽 위에 다시
    /// 스케치해도(그 벽의 세계 법선은 무리수다) 적을 수 없는 값이 나오지 않는다.
    /// 재귀는 잘 정초된다 — 프레임 없는 평면(세계 유리수 계수)에서 끝난다.
    ///     w = n/|n| ,  u = u_raw/|u_raw| ,  v = w × u
    ///     u_raw = (n·n)·ref_dir − (ref_dir·n)·n        ← 유리수, n 에 수직
    /// `ref_dir` 는 유도하지 않고 **저장한다** (유도 규칙이 바뀌면 모든 스케치가 조용히 돌아간다).
    /// `ref_dir × n != 0` 은 유리수 외적으로 정확히 검사한다.
    Frame { plane: Handle<Surface>, origin: [Rat; 3], ref_dir: [Rat; 3] },
}

// ★★ `Handle` 을 쓰므로 `Motion` 은 `nacre-topo` 로 내려간다. `nacre-scalar` 에 두려고 법선을
// `[Rat; 3]` 으로 인라인하면 **중첩 프레임에서 깨진다**(§「구현이 막힐 수 있는 자리」 5).
//
// ★★ `Frame` 은 앞의 셋이 누리던 지름길(`Axis::plane`, 축별 tol, `shared_base`, 미러 패리티,
// "90°계열은 tol 0")을 쓸 수 없다. 축 정렬 모션은 그 지름길을 **계속 쓴다** — 변종이 나뉘어
// 있으므로 일반형으로 후퇴하는 것은 `Frame` 이 사슬에 들어간 경우뿐이다.
//
// ★ 사슬 적용은 `chain[0]` 부터이므로 **새 모션은 leaf 이고 마지막에 적용된다** — 파라미터가
// 세계 좌표라는 뜻이다. `Frame` 이 법선을 이름으로 들기 때문에 그래도 성립하고,
// `parent` 가 뿌리 쪽을 가리키는 숲의 **꼬리 공유가 유지된다**(앞에 붙였다면 깨졌을 것이다).

// nacre-topo — 숲은 여기. Handle 이 필요하기 때문.
pub struct MotionNode {
    pub motion: Motion,
    pub parent: Option<Handle<MotionNode>>,   // 이력의 꼬리를 공유
}
```

## 평면

```rust
/// 곡면은 곧 그 곡면의 진실이다. f64 형태는 캐시 곁표에 있다.
/// 진실 없는 곡면은 만들 수 없다 — 변종이 곧 진실이다.
pub enum Surface {
    /// 계수를 모션 이력에 태운 평면. 계수는 **보관 시 정준화**한다 — 아래.
    Plane {
        /// ★ **모션 전 프레임**의 계수. `aX + bY + cZ + d = 0`.
        /// 모션이 붙으면 세계 좌표의 계수는 무리수일 수 있고, 그래서 여기 적지 않는다.
        coeffs: [Rat; 4],
        motion: Option<Handle<MotionNode>>,
    },
    // Cylinder { axis, radius, motion } / Sphere { .. } — M6 에서 각자의 진실로 추가
}

/// 진실의 f64 실현 — 진실과 **같은 모양**이다.
pub struct SurfaceCache {
    pub coeffs: [f64; 4],                     // [Rat; 4] 의 실현
    pub tol: [f64; 4],                        // 그 실현의 오차 (모션이 붙으면 쌓인다)
    pub inv_norm: f64,                        // 1/|n| — distance 가 나눗셈 없이 쓰도록
}
// distance(p) = (coeffs · [p, 1]) * inv_norm
```

★ 모션이 붙은 평면은 `coeffs` 에 tol 이 있으므로 **거리에도 오차가 따른다** —
그 산술 자체의 반올림과 함께 **소비자가 더한다**(오늘 `Plane::distance_eps` 가 하는 일).

지금의 `nacre_geom::Plane`은 한 평면을 **세 가지**로 들고 있다 — `origin`(위치),
`normal`(단위, 거리용), `raw`(원본, 계수용) — 그리고 `d`는 호출할 때마다 `−raw·origin`으로
**다시 만든다**. 그 f64 곱이 *"계수 평면 ≠ 그 점들이 만드는 평면"* 의 원인이었다.

진실이 `[Rat; 4]`가 되면 캐시는 **그것의 실현 하나**면 된다: `d`가 파생이 아니라 저장된 값이 되고,
서술이 하나가 되며, 진실과 캐시가 같은 모양이라 **반올림 사본임이 타입에 보인다.**

### 계수는 보관 시 정준화한다

평면은 **스케일 불변**이므로(`2x+4y−6=0` 과 `x+2y−3=0` 은 같은 평면) 대표를 하나 고를 수 있다.

```
[11/10, 3/5, 0, −7/2]
   ① 분모 털기 (lcm 곱)      → [11, 6, 0, −35]
   ② 내용(gcd) 나누기         → [11, 6, 0, −35]
   ③ 부호 규약 (첫 0 아닌 성분을 양수로)
```

★ 판정 때가 아니라 **보관 때** 하는 이유는 하나다: `==` 동일성은 **저장된 형태가 정준일 때만** 성립한다.

세 가지가 따라온다:

| | |
|---|---|
| **동일성** | 두 평면이 같은가 = 계수 네 개가 **비트 동일**한가. 술어가 아니라 `==` |
| **정확 경로** | 정수 계수가 `2^53` 안이면 f64 로 **정확** ⇒ Shewchuk expansion 이 부호를 증명한다 |
| **replay 결정성** | 같은 평면은 언제나 같은 비트로 저장된다 |

★★ **`frame_sign` 이 사라진다.** 부호를 정준화하면 평면에 고유한 법선 방향이 없어지고,
*"이 면이 그 법선을 그대로 쓰나 뒤집어 쓰나"* 는 **`Face::orientation` 이 이미 갖고 있다.**
오늘 평면 쪽에 있던 그 개념이 면 쪽 한 곳으로 모인다.

### 정규화 여부는 **값이 말한다** — 플래그를 두지 않는다

정준형의 세 조건은 전부 값에서 검사된다: 네 계수가 **정수**인가(`denom() == 1`),
분자들이 **서로소**인가, **부호 규약**을 지키는가. 플래그는 낡거나 거짓말할 수 있지만 값은 못 한다.

★ 그리고 두 소비자가 **서로 다른 조건**만 본다:

| 소비자 | 필요한 조건 | 만족하지 않으면 |
|---|---|---|
| `==` 동일성 | 정수 + 서로소 + 부호 규약 | 같은 평면인데 `!=` 로 읽힘 = **거짓 음성** ⇒ 기하 술어로 흘러간다 |
| 정확 경로 | 정수 + `2^53` 안 | 고정밀 상승(③)이 받는다 |

**둘 다 안전한 쪽으로 흘러간다.** `gcd == 1` 은 정확 경로에는 필요조차 없다 —
Shewchuk 은 f64 로 정확한 정수면 되고, 기약화는 `==` 동일성만을 위한 것이다.

★ **넘칠 때**: 분모의 lcm 이나 내용의 gcd 가 `Rat` 의 `i128` 을 넘으면 정규화하지 못하고
유리수 그대로 남는다. 그 평면은 위 두 검사에 자연히 걸려 안전한 경로로 간다 —
**별도 상태가 없다.** 정규화는 입력 계수의 **순수 함수**이므로 재생도 흔들리지 않는다.

★ 남는 실무 질문은 *"검사를 매번 할지, 캐시에 미리 계산해둘지"* 하나이고, 싼 검사라 **측정 후 판단**이다.

### 정확 경로에 크기 한계가 없다

`2^53` 은 *"계수가 f64 **하나**"* 의 한계이지 정확 산술의 한계가 아니다.
Shewchuk 의 `Expansion(Vec<f64>)` 은 **f64 여러 개의 정확한 합**이라, 성분을 늘리면 얼마든지 커진다.

| 저장된 계수 | 정확 판정 |
|---|---|
| 정수, `2^53` 초과 | 계수를 **`Expansion` 으로** 넘긴다 — `i128` 정수는 f64 2~3 성분이면 정확하다 |
| 정규화 실패해 남은 **일반 유리수** | ★ **술어 안에서 분모를 턴다** — 분자 × (다른 분모들의 곱) 을 `Expansion` 으로. 저장 시점에 `i128` 이 막던 것을 판정 시점에는 할 수 있다 |

★★ **`Expansion` 은 일반 유리수를 담지 못한다** — f64 들의 합이라 언제나 dyadic 이고, `11/10` 은
이진수로 유한하지 않다. 그래서 둘째 줄은 *"유리수를 expansion 으로 표현"* 이 아니라
*"분모를 털어 정수로 만든 뒤 expansion 으로 계산"* 이다.

⇒ **어느 쪽도 고정밀 상승으로 갈 필요가 없다.** 필터(f64)가 여전히 먼저 걸러내므로,
expansion 산술은 **애매한 경우에만** 돈다.

★ 없는 도구 하나: **`i128` → `Expansion`** (f64 세 조각으로 쪼개기). 오늘 `Expansion` 은
`two_product(f64, f64)` 처럼 f64 입력만 받는다.

### 구성의 순서가 뒤집힌다

```
지금:  점을 계산한다  →  그 점들로 면을 만든다
후:    ★ 면(계수)을 만든다  →  점은 세 면을 가리켜 **이름 붙는다**
```

★★★ 이것이 이 설계의 **가장 큰 구현 변화**다. `exact.rs` 가 좌표를 계산하던 자리가
*"프로파일의 변 → 벽 평면의 유리수 계수"* 로 바뀌고, 꼭짓점은 `{벽ᵢ, 벽ᵢ₊₁, 캡}` 이라고
**적기만** 한다. 사용자 치수는 점이 아니라 계수로 흘러간다.

★ 좌표는 이제 **세 평면을 푸는 것**으로 나온다. 비용은 3×3 풀이 ~20 flop 이라 무시할 만하고,
정확도도 오늘과 비슷하다 — 축 정렬은 정확하고, 회전은 몇 ulp 로 오늘의 회전 좌표와 같은 자릿수다.

**유도가 닫히는지 확인** — 스케치 프레임 안에서 프로파일 변 `(x1,y1) → (x2,y2)` 의 벽 평면은

```
(y2−y1)·X − (x2−x1)·Y + (x2·y1 − x1·y2) = 0        ← 유리수 곱과 차뿐
캡:  Z = 0  과  Z = dist                            ← 유리수
```

★★ **무리수가 한 번도 나오지 않는다.** 계수가 프레임 안의 것이고 모션이 나머지를 하기 때문이다.
그리고 그 평면들이 **프레임의 모션을 든다** — 그것으로 3D 배치가 끝난다.

### 모션은 평면에 다르게 작용한다

`Motion` 은 **점을 옮기는 것**으로 정의돼 있지만, 평면 계수에는 다른 식이 적용된다.
`SurfaceCache.tol` 이 어디서 오는지가 바로 이것이다.

| 모션 | 계수에 하는 일 | 정확한가 |
|---|---|---|
| `Translate(t)` | `n' = n`, `d' = d − n·t` | `n·t` 가 유리수 곱이면 **정확**(진실은 유리수다). f64 실현에서만 반올림 |
| `Rotate(axis, θ)` | `n' = R·n`, `d'` 는 pivot 보정 | 90°계열이면 정확. 그 밖에는 `cos/sin` 이 무리수라 **실현에 tol** |
| `Mirror(axis, c)` | 한 성분 부호 반전, `d'` 보정 | 대개 정확 |

★★★ 여기서 *"회전축에 수직인 평면은 계수가 정확히 보존된다"* 가 나온다 —
법선이 축과 나란하면 `R·n = n` 이고 `d` 도 그대로다. 그래서 그 판정은 **사슬을 보는 구조적 검사**로
할 수 있다(§「남은 것」 2b 의 각주와 같은 근거).

★ 진실 쪽(`[Rat; 4]` + 모션)에는 오차가 없다 — 오차는 **실현할 때** 생기고, 그것이 `tol` 이다.

### 정확 경로의 조건 — 세 평면이 같은 모션을 공유할 것

정점은 세 평면의 교차인데, 그 셋의 **모션이 서로 다르면** 세계 좌표에서 풀어야 하고
회전한 평면의 세계 계수는 **무리수**다. 그러면 정수 계수 위의 Shewchuk 경로를 쓸 수 없다.

| | |
|---|---|
| 세 평면의 모션이 **같다**(`None` 포함) | ★ 그 프레임 안에서 정수 계수 ⇒ **정확 경로** |
| 모션이 **섞인다** | 세계에서 실현 ⇒ f64 필터 + 고정밀 상승 |

★ 오늘의 `shared_base` 지름길이 정확히 이 원리이고(*"한 모션은 행렬식에서 상쇄된다"*),
*"회전 모델은 toleranced 경로"* 라는 현재 동작과도 맞는다.

### 같은 평면은 같은 핸들 — 평면을 interning 한다

계수를 정준화했으므로 *"두 평면이 같은가"* 가 `==` 다. 그래서 `push_surface` 는
**이미 있는 항목을 재사용**한다 — 모션 노드가 `(motion, parent)` 로 그러는 것과 같다.
우연히 같은 평면이라도 **같다고 판정되면 정말 같으므로**, 따로 둘 이유가 없다.

★ **구조가 같을 때만 합쳐진다.** `{coeffs: c, motion: None}` 과 `{coeffs: c', motion: m}` 이
기하적으로 같아도 구조가 다르면 별개다 — 회전한 평면의 계수는 무리수라 정준형으로 못 만든다.
그래서 기하 판정(②③)은 여전히 필요하다.

★★★★★ **그리고 그것은 이행이 끝나도 마찬가지다 — 정정(2026-08-01).** 이 문서의 초안은
*"② 가 완전해지면 ③(면 좌표)을 은퇴시킬 수 있다"* 는 전제로 쓰였는데, **틀렸다.**
구조 비교로는 잡을 수 없는 경우가 실재한다: 핀 배열에서 각도 `a` 인 핀과 `a+180` 인 핀은
**서로 다른 모션**으로 **같은 벽 평면**을 만든다. `(계수, 모션)` 이 다르므로 구조는 "다르다"고
답하지만 평면은 같다.

★★★★ **다만 정확히 답하는 범위는 넓힐 수 있다 — 모션을 대수적으로 다루면 된다.**
두 평면이 **같은 축·같은 피벗**으로 돌았다면 회전은 교환하고 각도는 더해지므로
`m_B⁻¹ ∘ m_A = Rotate(축, θ_A − θ_B)` 가 정확히 성립한다. 그 각이 90°계열이면 A 의 유리수 계수를
B 의 프레임으로 **정확히** 옮겨 `==` 로 비교할 수 있다 — 상승도 허용오차도 없이.
`(계수, 모션)` 형태여야 가능한 일이고, 이것이 목적지가 사주는 능력 중 하나다.
실측(2026-08-01): 갈래 ③ 에 도달한 24,215 쌍 중 **7,454 건(30.8%)** 이 그렇게 결정되고,
그 안에 **허용오차 병합 156 건이 전부** 들어간다. 상승 판정과의 불일치는 **0** 이다.

⇒ ①(핸들)과 ②(계수)와 ③′(모션 합성)은 **싸게 답할 수 있을 때 답하는 지름길**이고,
③(상승 판정)은 **최종 심급**이다.
무리수로 놓인 두 평면의 공면성은 정확 술어로만 답할 수 있고 `Judge::planes_coplanar` 가 그것이다.
실측: 핀 sweep 의 병합 630 건 중 **156 건이 오직 ③ 으로만** 닫히고, 그 156 건은 전부
`moved × moved` 다. 셋이 OR 로 묶인 것은 임시방편이 아니라 **올바른 구조**였다.

★★ 그러면 *"같으면 같은 핸들"* 이 **두 자리에서** 일어난다:

| | |
|---|---|
| **구성 시점** | interning — 정준 계수가 같으면 같은 핸들 |
| **판정 시점** | 불리언이 두 면을 한 평면 클래스로 묶으면 결과 면들이 **클래스 루트의 핸들**을 받는다 |

★ 그래서 `Face::surface` 비교(①)의 뜻이 *"출처를 공유한다"* 에서 **"진실이 같다"** 로 넓어진다 —
더 자주 답하고, 답할 때는 여전히 `O(1)` 이다.
interning 은 **결정적**이어야 한다(먼저 넣은 쪽이 이긴다) — 재생이 같은 핸들을 내야 하기 때문.

모델 캐시는 **f64 층만** 담는다. 고정밀 실현은 모델에 남기지 않는다 —
필요한 정밀도가 연산마다 다르고(`ProofStandard::start_bits`), 값이 크고, 판정이 끝나면 쓸모가 없다.

### 평면 클래스 계산이 줄어든다

불리언은 오늘 `plane_classes` 에서 **`O(n²)` union-find** 로 *"이 면들이 같은 평면인가"* 를 전부 묻는다
(80핀 fold 의 가장 큰 불리언: 406 면 / 172 surface). interning 하면 구조가 같은 평면은 구성 시점에
이미 한 핸들이므로 그만큼 물을 것이 없어진다.

★★ **다만 그 이득은 작다 — 측정했다(0단계, 2026-08-01): 피연산자 쌍 130 개, 평면 1560 개 중
이미 공유하는 것이 57 개(3.7%).** 나머지는 여전히 기하로 물어야 한다.
⇒ **interning 의 값은 속도가 아니라 동일성이다** — 같은 평면이 두 핸들로 갈리지 않는 것.

★★ 그리고 배열의 `Node::Seam([usize; 3])` 이 그대로 `Vertex { surfaces }` 가 된다 —
평면 클래스와 surface 핸들이 **같은 것**이 되기 때문이다.

### `validate` 의 일이 바뀐다

오늘 검사는 *"각 정점이 자기 면들 위에 tol 안에 있나"* 다. 새 설계에서 **정의하는 세 면 위에 있는 것은
구성상 자명**하므로 그 절반은 검사할 것이 없어진다.

★★ 남는 것이 진짜 질문이다: **정의하지 않는 나머지 인접 면 위에도 있나.**
각뿔 꼭대기처럼 면이 넷 이상 만나면 넷째 면이 그 검사 대상이고, 그것이 곧 **4-평면 동시성**이다
(오늘은 거절로 다룬다). ⇒ validate 가 *"좌표가 면 근처인가"* 에서
**"이 점이 정말 그 면들 전부 위에 있나"** 로 옮겨간다.

### 캐시의 세 범위

| 캐시 | 키 | 사는 동안 | 왜 |
|---|---|---|---|
| **모델 캐시** | 핸들 인덱스 (밀집) | 모델과 같이 | 모든 정점·면이 좌표를 가진다 |
| **고정밀 메모** | (정의, 정밀도) (희소) | **연산 하나** | 판정이 실제로 만든 정의점에만 붙는다 — 모델 정점 수천 개 중 수백 개 |
| **각도 캐시** | 각도 (+정밀도) | **프로세스(스레드)** | 값이 키의 순수 함수다 — `cos 37°` 는 어느 모델에서나 같다 |

★ 그리고 모델 캐시는 **도달 가능한 것만 채워도 된다.** 아레나는 append-only 라 옛 정점이 남지만,
캐시는 버릴 수 있으므로 live 솔리드에서 닿는 것만 실현하고 나머지는 비워둔다.

셋은 **인덱스 공간이 다르므로 합치지 않는다.** 고정밀을 핸들 인덱스로 밀집 배열에 담으면
대부분이 비고, 더 나쁘게는 *"모든 점을 실현한다"* 는 뜻이 된다 —
`trial_bound`가 일부러 캐시를 우회하는 이유가 정확히 그것이다.

## 판정 (연산 동안만 산다)

```rust
// nacre-cip — 점은 하나, 층은 평면이 진다.

/// 판정용 점 — 세 평면을 가리키기만 한다.
/// ★ 좌표를 만들지 않는다. 캐시하는 것은 **나누지 않은 좌표**(동차좌표)다.
pub struct WorkingPoint<'a> {
    pub planes: [&'a WorkingPlane; 3],
    homog: OnceCell<[Approx; 4]>,              // [X : Y : Z : W] — f64 층만
}

/// 판정용 평면 — 정의를 펼쳐 들고, 두 실현을 메모한다.
pub struct WorkingPlane {
    // 정의
    pub coeffs: [Rat; 4],
    pub chain: Rc<[Motion]>,                   // 사슬을 펼친 것 (핸들은 판정 층에서 못 푼다)

    // 실현 1 — f64, 항상
    pub cache: SurfaceCache,                   // 모델과 같은 타입

    // 실현 2 — 고정밀, 필요할 때만
    hp: Rc<OnceCell<(usize, HpSurfaceCache)>>, // 정밀도와 함께
}

/// 이 연산에서 **무엇을 증명으로 인정하나**. 한 연산 동안 고정된다.
/// ★ 설정이 하나도 없다 — 전부 모델에서 유도된다.
pub struct ProofStandard {
    /// 모델의 크기(가장 큰 좌표 크기). 표 전체에서 취해 **순회 순서에 무관**하다(재생 결정성).
    pub model_size: Mag,
    /// 유도 — `same_within()` 에 닿도록 모델에서 계산한 시작 정밀도.
    pub start_bits: usize,
    /// 유도 — **비용** 한계이지 해상도 한계가 아니다. 산술은 어느 깊이에서도 옳다.
    pub max_bits: usize,
}

impl ProofStandard {
    /// f64 출력 해상도(`model_size · 2⁻⁵²`)보다 **두 워드 아래** = `model_size · 2⁻¹⁸⁰`.
    /// 이보다 가깝다고 **증명되면** 같은 것이다.
    ///
    /// 낮게 잡으면 비트만 더 쓰지만 높게 잡으면 **진짜로 떨어져 있던 것을 합친다** —
    /// 그 비대칭이 아래로 밀라고 말한다. 워드가 단위인 것은 astro-float 가 워드로 할당하기 때문.
    ///
    /// ★ **사용자 설정이 아니다.** 더 거칠게 두는 것은 전역 tolerance 라 DNA 가 금지하고
    /// (이 커널은 치유하지 않고 거절한다), 더 정밀하게 두는 것은 **출력에서 살아남지 못해** 무의미하다.
    pub fn same_within(&self) -> Mag { … }
}

pub enum Decision {
    Sign(Orient),                              // 증명된 부호
    Coincident { within: Mag },                // 한계 안이라고 증명됨 — 근거 포함
    Exhausted { at: usize, within: Option<Mag> },
    Degenerate,
}
```

★★★★ **「정의 + 두 실현」 이라는 층이 평면 한 곳에만 있다.** 점은 평면 셋을 빌려 보는 얇은 값이고,
좌표를 만들지 않으므로 좌표 실현이라는 층 자체가 없다 — 대신 **동차좌표**를 메모한다.
`x = X/W` 인데 **나누지 않는다**: 나누면 무리수가 되고 오차가 낀다. 부호 질문은
`sign(X − …·W) · sign(W)` 처럼 **곱셈과 뺄셈만으로** 답한다 — 그것이 indirect 술어다.

★ `homog` 가 f64(`Approx`) 층만 두는 것은 의도다 — **평면의 고정밀이 이미 메모되어 있으므로**
점의 고정밀은 거기서 다시 계산한다. 층을 두 번 두면 두 곳이 어긋날 수 있다.

이름이 **수명을 말한다**: `Vertex`·`Surface` 는 모델에 살고, `Working…` 은 연산 동안만 산다.
`Model` 에 `Working…` 을 담는 코드는 읽는 즉시 이상해 보여야 한다.

고정밀 메모는 `Rc` 라 복제본끼리 **공유**된다: 한 평면은 연산 동안 **한 번만** 실현되고,
연산이 끝나면 `WorkingPlane` 과 함께 사라진다. 정밀도를 값과 함께 들어서,
상승이 더 깊이 가면 그 항목이 교체된다.

★ `coeffs`·`cache` 는 고정 크기라 **복사**하고, `chain`·`hp` 는 가변 길이/공유라 `Rc` 다.
전자를 `Rc` 로 두는 안은 **접었다** — memcpy 가 평면마다 힙 할당과 간접 참조를 사는 것보다 낫고,
f64 필터가 가장 뜨겁게 읽는 `cache` 도 같은 이유로 인라인이다.
`WorkingPoint` 는 평면표를 **빌려** 보므로 아무것도 소유하지 않는다.

★ 연산을 넘겨 유지할지는 **재보지 않은 성능 질문**이다: 다음 연산은 평면표를 다시 만들어
작업 평면들이 새 객체가 되고, 정밀도도 다시 정해진다.

### 실현 통로는 하나다

```rust
/// 한 점을 원하는 정밀도로 실현한다. **판정도 출력도 이 통로를 쓴다.**
fn realize(p: &WorkingPoint, bits: usize) -> HpPointCache
```

| 소비자 | |
|---|---|
| 판정 | 상승하며 `bits` 를 올린다 |
| 테셀레이션·표시 | ★ **쓰지 않는다** — f64 캐시로 충분하다 |
| STEP 출력 | `realize(p, 128)` → `round_to_f64` 로 **정확 반올림**해 f64 로 낸다 |
| (원하면) | 더 깊은 `bits` 로 더 정밀한 출력 |

★★ 통일안에서 실현은 *"세 평면을 `bits` 정밀도로 풀고 나눈다"* 이다. 정밀도를 올리면 좌표가 좁아지므로,
**세 평면 풀기의 나눗셈 오차는 출력 시점에 해소된다** — 모델 캐시가 f64 한 층만 들고도 되는 이유다.

### 수치 층

같은 것의 다른 정밀도는 **`Hp` 접두사 하나로만** 다르다.

```rust
// nacre-scalar — f64 가 담을 수 없는 범위의 양의 크기 (m · 2^e, e: i64).
// 값은 언제나 >= 0 이고, 산술은 **보수적**이다: 저장된 값이 참값보다 작아지지 않는다.
pub struct Mag { m: f64, e: i64 }

// 중간 계산값 — 행렬식·여인수·내적 같은 **스칼라**. 캐시는 이것을 쓰지 않는다.
pub struct Approx   { value: f64,      error: f64 }
pub struct HpApprox { value: BigFloat, error: Mag }

// 캐시 — 넷 다 「값 배열 + 오차 배열」 로 같은 모양이다.
pub struct PointCache     { coord: Point3,          tol: [f64; 3] }
pub struct HpPointCache   { coord: [BigFloat; 3],   tol: [Mag; 3]  }

pub struct SurfaceCache   { coeffs: [f64; 4],        tol: [f64; 4], inv_norm: f64 }
pub struct HpSurfaceCache { coeffs: [BigFloat; 4],   tol: [Mag; 4] }
```

**평면 계수에도 오차가 있다.** 모션이 붙으면 회전한 계수의 실현은 점의 좌표와 똑같이 오차가 쌓인다.

오차 필드는 넷 다 **`tol`** 이다 — DNA 원칙 4가 tol 을 *"relaxation의 실측 달성치"* 로 정의하고,
그것이 정확히 캐시가 담는 것이다(옛 `Origin::Discovered { tol }` 이 여기로 옮겨온 것이기도 하다).

값과 오차를 **묶지 않고 배열 둘로** 두는 이유는 f64 쪽에 있다 — `coord: Point3` 를
tess·props·STEP·geom 이 **그대로 받는다.** 묶으면 그때마다 뽑아내야 한다.
고정밀 쪽은 소비자가 판정뿐이라 어느 쪽이든 되므로, **f64 쪽에 맞춘다.**

`inv_norm` 의 고정밀 쌍둥이는 두지 않는다 — 판정은 거리가 아니라 행렬식으로 답한다.

## 각도 캐시 — 그리고 프레임 (nacre-scalar, thread_local)

```rust
/// π 등 — **상수**이지 결과가 아니다. 고정밀 층이 라디안 변환·인자 축약에 쓴다.
static HP_CONSTS: RefCell<Consts>;

/// 고정밀 cos/sin. 정밀도가 다르면 다른 값이므로 **정밀도가 키에 들어간다.**
static HP_TRIG: RefCell<HashMap<(Angle, usize), HpTrig>>;

/// f64 cos/sin 과 **그 실현의 tol**. 각도만으로 키를 잡는다 — 값이 정확 반올림이라 유일하다.
static F64_TRIG: RefCell<HashMap<Angle, F64Trig>>;

pub struct HpTrig  { cos: HpApprox, sin: HpApprox }   // 값과 tol 이 한 덩어리
pub struct F64Trig { cos: Approx,   sin: Approx   }   // ★ 완전히 대칭

/// ★ 2b. `Motion::Frame` 의 실현은 `1/|n|` 과 `1/|u_raw|` 뿐이고, 둘 다 **유리수의 역제곱근**이다.
/// 삼각함수와 **같은 모양**이다 — 키의 순수 함수이고, 정밀도가 다르면 다른 값이다.
static HP_INV_SQRT:  RefCell<HashMap<(Rat, usize), HpApprox>>;   // 키는 n·n (유리수)
static F64_INV_SQRT: RefCell<HashMap<Rat, Approx>>;
```

★★★ **프레임이 새 종류의 캐시를 요구하지 않는다.** `Angle` 대신 `Rat` 을, `cos` 대신 `√` 를 넣은
같은 표다. 정확 반올림 규율(값이 유일하므로 tol 도 유일)도 그대로 선다. ⇒ 2b 가 수치 층에
가하는 부담은 **표 하나**다.

★★★ **값과 tol 을 한 표에 둔다.** 옛날에는 한 각도의 f64 실현이 여러 개 공존할 수 있어서
(libm 호출과 컴파일러가 상수 폴딩한 값이 1 ulp 달랐다) tol 을 *"어느 쌍에 대해 잰 것인가"* 로
따로 키잡아야 했다. **정확 반올림이 그 이유를 없앴다** — 실현이 유일하면 tol 도 유일하다.
⇒ 값에 안 맞는 tol 을 꺼내는 길이 **타입에 없다.**

★ 비용도 없다: f64 실현을 만들 때 고정밀 값이 이미 손에 있으므로 tol 은 **뺄셈 하나**다.
`PointCache` 의 원칙(*"실현과 그 정확도는 함께 만들어지고 함께 버려진다"*)이 여기에도 그대로 선다.

★★ **이 셋만 전역(스레드 수명)이다.** 값이 **키의 순수 함수**이기 때문 — `cos 37°` 는 모델과
무관하게 늘 같다. 모델이 바뀌어도, 연산이 끝나도 낡지 않는다.
`thread_local` 인 이유는 병렬 불리언의 워커마다 자기 것을 갖게 하기 위해서다
(공유 잠금을 피한다; 대신 워커마다 π 를 한 번씩 만든다).

## 구현이 막힐 수 있는 자리 — 그리고 그 대안

늦게 터지면 되돌릴 것이 많은 위험만 모았다. **하나도 막다른 길이 아니다** — 1 은 비용을 치르고
닫혔고(2b 채택), 2·5·7 은 확인으로 닫혔고, 3·6 은 분량 문제이며, 4 는 M6 의 알려진 절벽이다.
★ 5·6 은 **2b 를 채택하면서 새로 생긴 것**이다 — 결정 하나가 위험 지도를 바꾸므로 다시 훑는다.
★★★ 8·9·10 은 성질이 다르다: 설계가 **틀렸는가**가 아니라 **거기까지 안전하게 갈 수 있는가**이고,
그것이 *"끝에 가서 다 되돌린다"* 의 실제 원인이다. ★★ 셋 다 닫혔다 — 8 은 관문을 갈아 끼우고,
10 은 규율이며, 9 는 **추가-후-삭제**로 쪼개진다. 그리고 **0단계 측정이 착수 전에 설계를 반증할 수 있다.**

### 1. 유리수 계수를 못 만드는 평면 — **2b 로 간다** (결정: 2026-08-01)

기울어진 면 위에 스케치하면(옆벽 `PadOnFace` 는 흔하다) 새 벽들의 세계 좌표 계수가 무리수다.
`Surface::Plane { coeffs: [Rat; 4] }` 에 넣을 값이 없어 보이고, `Inexact` 는 지웠다.

#### 기각한 안 — f64 계수를 `Rat` 으로 들어올리기

들어올리기 자체는 무손실이다(모든 유한 f64 는 정확히 유리수). **위험한 것은 그 다음이다.**

★★★★ **반올림이 진실에 구워진다.** 계산된 f64 계수를 *"이것이 진실"* 이라고 선언하는 순간,
그 평면은 사용자가 요구한 평면이 **아니다** — 1 ulp 안이지만 정확히 다르다. 그리고 같은 벽이
두 경로로 도달하면(원래 프리즘 벽 vs 그 위의 `PadOnFace`) 반올림이 갈려 **한 벽이 두 평면 클래스**가
된다. 임의정밀 술어는 그 둘이 다르다는 것을 **정확히, 확신을 갖고, 영구히** 증명한다.

★★★ **이 문서를 쓰게 만든 병과 같은 병이다.** §1.1 의 `Discovered` 꼭짓점을 `Pt3::exact` 로
승격하던 것 — *"오차가 base 유리수에 구워지므로 정밀도로 고칠 수 없다"* — 가 평면 쪽에서
같은 모양으로 반복된다. interning 이 그것을 **모델의 영구한 동일성**으로 굳히므로 더 나쁘다.

★★ 게다가 **`i128` 폭탄**이다. 들어올린 f64 는 `mantissa · 2^exp` 라 분모가 `2^50` 급이고
(`0.1` → `3602879701896397/2^55`), 계수 넷의 분모를 털면 정준화가 곧바로 넘친다 ⇒ 유리수 가지로
떨어져 모든 술어가 큰 수를 끌고 다닌다.

#### 채택한 안 — 2b (프레임을 정의로 든다)

무리수를 **계수에 담지 않고 모션에 담는다.** 프로파일의 변은 스케치 프레임 안에서 유리수 계수의
평면이고, 그 평면이 프레임 모션을 든다. 진실에 반올림이 들어가지 않는다.

★★★★ **이것은 새로운 종류의 문제가 아니다.** `Motion::Rotate` 는 **이미** 무리수 계수를 만든다 —
30° 회전의 `cos30 = √3/2` 다. 커널은 그것을 유리수로 적으려 하지 않고 **정의로 들고 있다가
필요한 정밀도로 실현**한다(`HpTrig`). 프레임 모션은 *유리수의 `cos`* 대신 *유리수의 `√`* 일 뿐,
같은 통로(`realize`)를 탄다. **가능성의 문제가 아니라 지름길의 문제다.**

★★★ 그리고 프레임의 회전 부분은 **스케일을 빼면 유리수다.** `n`, `ref_dir` 이 유리수일 때

```
u_raw = (n·n)·ref_dir − (ref_dir·n)·n        ← 유리수, n 에 수직
v_raw = n × u_raw                            ← 유리수
```

무리수인 것은 **단위 길이로 나누는 것뿐**이다. 부호만 묻는 술어(`orient3d`)는 양의 행렬식을 갖는
어떤 선형사상에도 불변이므로 **정규화 없이** 답할 수 있다.
★ 단, 세 축 길이가 `|n|`, `|u_raw|`, `|n||u_raw|` 로 **서로 다르다** — 유리수 배로 같게 만들려면
`|u_raw|` 가 유리수여야 하므로(피타고라스 조건) 일반적으로 불가능하다. ⇒ 등방이 아니라서
**좌표 비교(`cmp_coord`)와 프레임 간 비교는 그대로 쓸 수 없다.** 어디까지 정규화 없이 가는가는
구현 시 잴 항목이지, 막히는 자리는 아니다(막히면 `realize` 로 간다).

★★ **치를 대가는 문서가 이미 적어둔 그대로다**(§「남은 것」 2b): `Motion` 이 축 정렬 밖으로 나가면
그 전제 위에 선 지름길들(`Axis::plane`, 축별 tol, `shared_base`, 미러 패리티, *"90°계열은 tol 0"*)을
일반형으로 다시 써야 한다. **비용은 지름길이지 정확성이 아니다.**

### 2. interning × 병렬 불리언 — **확인했다, 문제 없다**

워커들이 동시에 `push_surface` 하면 삽입 순서가 실행마다 달라지고, **핸들 번호가 달라져 replay 가
같은 모델을 못 낸다**(DNA 원칙 3). 그리고 이것은 **대장이 실행마다 흔들리는 것**으로 늦게 나타나
원인 찾기가 어렵다.

| 대안 | |
|---|---|
| ★ **(a) 순차 구간에서만 push** | 결과 조립은 이미 순차다. **불리언이 새 surface 를 만드는지** 지금 grep 으로 확인된다 |
| ★★ **(b) 정렬 후 일괄 push** | 새 surface 를 모아 **정준 키로 정렬**해 넣는다 ⇒ 발견 순서와 무관하게 결정적. (a) 가 아닐 때의 확실한 폴백 |
| (c) interning 포기 | 이득을 잃는다 |

★★★ **(a) 가 성립한다 — 실측(2026-08-01).** `push_surface` 의 프로덕션 호출부는
`ops.rs`(extrude/pad) 셋과 `transform.rs` 하나뿐이고 **전부 순차 경로**다.
나머지는 `add_cuboid` 같은 test-util 과 테스트다. ★ **불리언은 `push_surface` 를 아예 부르지 않는다** —
결과 면은 피연산자의 surface 를 재사용한다(`planes[lf.plane_idx].surf`).
그리고 rayon 은 `par.rs` 한 곳에만 있고, *"rayon 은 여기 말고 어디에도 나오지 않는다"* 를
**텍스트 검사 테스트**가 지킨다.

★ **지켜야 할 불변식으로 남는다**: 병렬 구간에서 `push_surface` 가 생기면 재생이 깨진다.
M6 에서 교차 곡면을 만들게 되면 여기를 다시 본다. 그때는 (b) 로 간다.

### 3. 평면-under-모션의 오차 한계 — 새로 유도해야 하지만 **처음부터는 아니다**

오늘의 오차 기계는 **점이 모션을 지날 때**를 위한 것이고, **평면 계수가 모션을 지날 때**의 한계는 없다.
여기서 틀리면 건전성이 깨진다(조용한 오답).

★ 다만 **법선은 점과 같은 식**이다 — `n' = R·n` 은 `p' = R·p` 에서 pivot 항만 뺀 것이라
기존 유도를 재사용한다. 새로 붙일 것은 `d` 의 변환 항뿐이다. ⇒ 분량은 있으나 **미지의 유도가 아니다.**

### 4. M6 절벽 — 통일안을 채택했으므로 **모든 점**에 걸린다

이차곡면 셋은 교점이 최대 8개라 `Vertex { surfaces }` 가 점을 지목하지 못한다(§「남은 것」 5).
평면만 있는 M5 에서는 문제가 없지만, **M6 를 열 때 정점 표현을 다시 봐야 한다**는 것을 알고 시작한다.

### 5. ★★★★ 중첩 프레임 — **찾아서 고쳤다** (2026-08-01)

2b 의 `Frame` 을 `{ origin, normal: [Rat;3], ref_dir }` 로 적으면 **막힌다.**

사슬은 `chain[0]` 부터 적용되고 새 모션은 leaf 라 **파라미터가 세계 좌표**다. 그런데 옆면 스케치가
만든 벽면은 **세계 법선이 무리수**이므로, 그 벽 위에 다시 스케치하면(흔하다) `normal` 에 적을 값이 없다.
★ 그리고 *"프레임을 사슬 앞에 붙이자"* 도 안 된다 — `MotionNode { parent }` 는 **뿌리 쪽을 공유**하므로
앞에 붙이려면 사슬 전체를 새로 만들어야 하고 꼬리 공유가 무너진다.

★★★★ **법선을 성분이 아니라 이름으로 든다** — `Frame { plane: Handle<Surface>, origin, ref_dir }`.
`origin`·`ref_dir` 는 **그 평면 자신의 프레임 안**의 유리수이고, 재귀는 프레임 없는 평면에서 끝난다.
leaf 추가라 꼬리 공유가 유지되고, 세계 유리수 법선이 애초에 필요 없다.
대가는 `Motion` 이 `Handle` 을 쓰므로 **`nacre-scalar` → `nacre-topo`** 로 내려가는 것 하나다.

★★ **교훈**: *"셋 다 유리수라 안전하다"* 는 **한 겹만 볼 때** 참이었다. 이 설계는 평면의 진실이
다른 평면을 가리킬 수 있게 만들었으므로, 새 필드마다 **한 겹 더 중첩했을 때** 를 물어야 한다.

### 6. ★★★ `Frame` 의 정준화 — 그것이 곧 interning 키다

`n` 과 `2n`, `ref_dir` 과 `ref_dir + λn` 은 **같은 프레임**이다. 정준화하지 않으면 같은 면이 두 핸들을
받고, 그러면 평면 클래스가 갈린다 — 이 문서가 없애려는 병 그대로다.

★ **계수 정준화와 같은 방식으로 닫힌다**: `ref_dir` 을 `u_raw = (n·n)·ref_dir − (ref_dir·n)·n` 의
**원시 정수 형태 + 부호 규약**으로 바꾼다. 같은 프레임이면 `==`. `i128` 이 넘치면 정규화가 실패하고
기하 판정으로 안전하게 강등된다 — 계수 쪽과 **같은 규율**이다.

★ 남는 것: 한 면 위의 스케치 둘이 `origin` 이 달라 프레임이 갈린다. 정준 원점(수선의 발 —
그 평면의 프레임 안에서 유리수)으로 **유도**하면 하나로 합쳐지지만, *"유도 규칙이 바뀌면 모든 스케치가
조용히 어긋난다"* 는 `ref_dir` 때와 같은 취약성이 생긴다. ⇒ **옵션으로 남긴다.**

### 7. 사슬 정준화 — 확인했다, 깨질 것이 없다

`Frame` 이 모션 사슬의 재작성 패스를 깰까 걱정했으나 **그런 패스가 없다**(코드 확인 2026-08-01):
`Loop::reversed` 는 루프용이고, 패리티는 모션마다 `reverses_orientation()` 으로 즉시 처리된다.
`Frame` 은 `det = +1` 이라 패리티에 아무것도 보태지 않는다.

### 8. 좌표가 바뀌는 만큼 **비트 동일 관문이 헐거워진다** — 관문을 갈아 끼운다

이 커널의 대규모 리팩터 관문은 늘 *"대장이 비트 단위로 같은가"* 였다. 좌표를 직접 계산해 저장하던 것이
**세 평면을 푸는 것**으로 바뀌므로 일부 좌표가 달라진다 — **의도된 변화**다. 그만큼 *"의도된 변화"* 와
*"방금 넣은 회귀"* 를 가르지 못한다.

★★★ **다만 전부 바뀌는 것은 아니다.** 축 정렬 상자의 꼭짓점은 `x=a, y=b, z=c` 를 푸는 것이 나눗셈
없이 그대로 답이라 **비트 동일**하다. 실제로 3×3 을 푸는 것만 달라진다. ⇒ *"안전망이 사라진다"* 가
아니라 **"일부에서만"** 이고, **얼마나인지는 재보면 안다** — 착수 전에 잴 것이 아니라 1단계 후에 나온다.

| 관문 | |
|---|---|
| **1차** | 대장 **비트 동일**. 통과하는 픽스처는 이것으로 끝난다 |
| **2차** | 깨진 것만: **위상 정확 일치**(면·모서리·정점 수와 인접) **+ 좌표가 ε 안** |

★ ε 는 *"이 점이 다른 곳으로 갔는가"* 를 묻는 값이므로 **모델 크기 상대**로 잡는다. 절대값은 큰
모델에서 헐겁고 작은 모델에서 조인다. ★★ 값은 **측정으로 정해졌다**(0단계): 세 평면 풀이와 저장
좌표의 차이가 최대 **지름의 `2⁻⁵¹·³`** 이므로 **`2⁻⁴⁰` 은 2000배 여유**다 — 반올림 차이는 다 통과하고
기하가 움직이면 걸린다.
★★ 위상 일치가 **함께** 걸려야 의미가 있다 — 구조가 그대로인데 좌표만 ε 안에서 움직였으면
그것은 반올림 차이지 기하 변화가 아니다.

★★★ **합격/불합격이 아니라 숫자를 찍는다.** 픽스처 전체의 **최대 편차**를 출력하면 임계값 아래에 숨는
**누적 드리프트**(불리언을 연쇄할수록 조금씩 밀리는 것)가 그 숫자가 자라는 것으로 드러난다.
관문만 두면 그것은 조용히 통과한다.

★ **버린 안**: *"`|새 − 옛| ≤ 그 정점이 기록한 tol`"* 은 실행 불가능하다 —
**`Constructed` 정점에는 tol 이 없다**(그것이 DNA 의 구분 그 자체다). 비교할 기준값이 존재하지 않는다.

### 9. 이행 — **더할 수 있으므로 한 번에 갈아엎지 않는다**

구성 순서가 뒤집히므로(점→면 ⇒ 면→점) 생성자 전부가 함께 바뀌어야 하고, 중간에 테스트를 못 돌리면
**막히는 지점이 끝에서만 드러난다** — 처음엔 그렇게 판단했다. ★★★★ **틀렸다: 삭제만 생각했고
추가를 빼먹었다.**

**0단계 — 측정했다 (2026-08-01). 반증되지 않았고, 설계가 예상보다 단순해졌다.**

대장 130 케이스의 결과와 **피연산자 양쪽**(4000 정점: Constructed 1304 / Discovered 1992 /
Moved 704) + 대장에 없는 **4-평면 동시성** 픽스처(`cube_and_spun_bar(0.2, 45°)` + 융합 블록).

| 질문 | 답 |
|---|---|
| 모든 정점이 세 평면으로 지목되나 | ★★★★ **4018 정점 전부 인접 면이 정확히 3개** — 4-평면 동시성 케이스까지 |
| 삼중을 어떻게 고르나 | ★★★ **고를 것이 없다** — 후보 삼중이 언제나 정확히 하나다 |
| 잔차 = ε 는 얼마여야 하나 | 최대 **지름의 `2⁻⁵¹·³`** (Constructed 만 보면 `2⁻⁵⁴·¹`) ⇒ 제안한 `2⁻⁴⁰` 는 **2000배 여유** |
| 삼중의 조건수 | 최악 `|det|/|n|³ = 0.5` (Constructed 는 `1.0`) — **병든 삼중이 없다** |
| interning 이득 | 피연산자 쌍 130, 평면 1560 중 **공유 57 = 3.7%** |

★★★★ **"네 평면이 한 점에서 만난다" 는 "네 면이 그 정점에 모인다" 가 아니다.** 4-평면 동시성은
배열이 겪는 일이고, 결과 정점의 인접 **면**은 여전히 셋이다. ⇒ `[Handle<Surface>; 3]` 이
**오늘 커널이 만들 수 있는 모든 정점**을 지목한다. 풍차·각뿔 걱정은 현행 연산(돌출 + 프리즘 불리언)
에서는 발생하지 않는다 — 훗날 loft·revolve·chamfer 가 오면 다시 물어야 하고,
그때를 위해 *"결정적으로 비퇴화 셋을 고른다"* 규칙은 **명세로 남기되 급하지 않다.**

★★ **정정 — 「평면 클래스 계산이 줄어든다」는 과장이다.** 구성 시점 interning 이 걷어낼 수 있는 것은
피연산자가 이미 공유하는 평면뿐이고 **3.7%** 다. interning 의 값은 **속도가 아니라 동일성**이다.

★ 측정의 한계(정직하게): 인접 면은 **면 → 루프 → 모서리 → 정점** 으로 세었으므로, 모서리 없이
면이 정점에 닿는 접촉은 세지 않는다. 그런 접촉은 비다양체라 커널이 거절한다.
★★ 그리고 첫 측정은 **불리언 결과만** 보아 `Constructed` 가 0 이었다 — 설계를 자동으로 만족하는
집단만 잰 것이었다. 피연산자를 넣어야 세 origin 이 다 나왔다.
(프로브는 일회용이고 되돌렸다. 재유도 가능: 정점→인접 surface 맵을 만들고, 삼중을 Cramer 로 풀어
저장 좌표와 비교하고, `|det|/|n|³` 으로 조건수를 본다.)

**단계.**

| 단계 | 무엇 | 관문 |
|---|---|---|
| **0** | 위 측정 (읽기 전용) | ✔ **완료 2026-08-01 — 반증되지 않았다** |
| **1** | 평면의 진실 정리 — 계수 정준화 + interning | 위상 정확 + ε |
| **3a** | ★ `Vertex` 에 `definition: [Handle; 3]` 을 `point` **옆에** 추가. 모든 생성자가 채운다. 대장 전체에서 *"정의를 풀면 `point` 와 일치하는가"* 를 단언 | **답을 안 바꾼다** ⇒ 비트 동일 |
| **3b** | 단언이 초록이면 `point` 를 지운다 | 위상 정확 + ε |
| **2** | `Motion::Frame` + 2b | 새 픽스처와 함께 |

★★★★ **3a 가 이행의 심장이다.** 필드만 늘어나므로 옛 관문이 그대로 살고, 초록이라는 것은
*"세 평면으로 모든 정점을 지목할 수 있다"* 는 **핵심 전제가 실측으로 확인됐다**는 뜻이다.
위험이 마지막에 몰려 있던 것이 아니라 **중간에서 확인 가능하다.**

★★★ **2b 를 마지막에 두는 이유**: 옆면 스케치 픽스처가 오늘 대장에 없다. 먼저 넣으면
**테스트 없는 새 복잡도**를 다른 단계 내내 끌고 다니게 된다. 2 와 3 은 서로 독립이다
(정점이 명시든 암시든 2b 는 성립한다).

★★ **1 이 좌표 중립이라고 단언하지 않는다(정정).** interning 이 두 surface 를 합치면 결과 면이 받는
**평면 클래스 루트**가 달라지고, 그 면의 f64 계수가 바뀌어 배열이 계산하는 교차 좌표가 몇 ulp 움직인다.
⇒ **위상 정확 + ε 를 이행 전 구간의 기본 관문으로 두고, 비트 동일은 보너스 신호로 읽는다.**

### 10. ★★★★ 성능 절벽 — 이 커널에 **선례가 있다**

모든 점이 암시가 되면 좌표를 쓸 때마다 세 평면을 푼다. *"3×3 풀이 20 flop 이라 무시할 만하다"* 는
**연산 하나의 비용**이지 **호출 횟수**가 아니다.

★★★★ 회전 불리언이 느렸던 진짜 원인은 astro-float(8%) 이 아니라 **`plane_def` 가 판정마다 정의를
다시 만들던 것(77%)** 이었고, 고치자 브라우저에서 **25초 → 0.4초** 였다. 같은 함정이 여기 그대로 있다.

⇒ 규율로 못박는다: ★★★ **f64 좌표는 즉석에서 다시 풀지 않는다 — 표에서 읽기만 한다.**
모델 캐시가 비어 있는 경로(`trial_bound` 처럼 일부러 우회하는 곳)를 **세어서** 확인한다.

### 11. STEP 가져오기 — **하지 않는다**

외부 파일에서 읽은 모델은 **정의 없이 좌표만** 있으므로 `f64 → 정확` 을 요구한다 —
이 설계가 금지하는 방향 그대로다. ★ **가져오기는 하지 않기로 결정돼 있다**(2026-08-01 재확인;
overview.md 「범위」의 v1 비목표보다 강한 결정). ⇒ 위험이 아니다.

## 남은 것 — 옵션과 미정

1. **큰 계수의 정확 부호 — 결정할 것은 없고, 만들 것과 잴 것만 있다.**

   **만들 것**
   - `i128 → Expansion`: 53비트 조각 셋으로 쪼갠다(`x = hi·2^106 + mid·2^53 + lo`).
     2의 거듭제곱 곱은 f64 에서 정확하므로 변환 전체가 오차 0이고, 조각은 크기 오름차순으로 둔다.
   - 술어가 `[Expansion; 4]` 계수를 받게 한다 — 안쪽 산술은 이미 expansion 이라 구조는 그대로다.
   - 정규화 실패해 유리수로 남은 계수는 **술어 안에서 분모를 턴다**(분자 × 다른 분모들의 곱).

   **잴 것**
   - 성분이 1 → 3 으로 늘 때 정확 경로가 얼마나 느려지나. (참고: `BigFloat` 실현 한 번이 **32µs**,
     expansion 산술 수십 번은 1µs 미만이므로 고정밀보다는 여전히 훨씬 싸다.)
   - ★ 더 중요한 것 — **실제로 몇 %가 3조각을 필요로 하나.** 정준화 후 계수의 비트 폭 분포를
     커버리지 전체에서 찍으면 나온다. 일반적인 CAD 치수(`123.456` = `123456/1000`)면 계수가
     대략 `2^40~2^50` 이라 **조각 하나로 끝날 공산이 크다** — 그러면 비용이 아예 안 난다.
   - 그리고 f64 필터가 먼저 걸러내므로 expansion 경로는 **애매한 ~1%** 에서만 돈다.
2. **구성 산술을 모션으로 — 2a 는 옵션, ★ 2b 는 확정이다(2026-08-01).**

   돌출은 꼭짓점을 `origin + x·u + y·v + normal·dist` 로 **계산**한다. `exact.rs` 가 그것을
   유리수로 하고(그래서 `7.7` 돌출과 `1.1`+`6.6` 돌출이 같은 평면에 앉는다), 스케치 축이 유리수가
   아니면 **거절**하고 f64 경로로 떨어진다. **커널에 유리수 산술이 남은 유일한 자리**이고
   `i128` 오버플로 압력도 여기뿐이다.

   아이디어는 **계산하지 말고 기록하는 것**이다: 스케치 프레임 안에서는 `(x, y, 0)` 과
   `(x, y, dist)` 가 전부 유리수이고, 무리수는 **그것을 3D 로 옮길 때** 생긴다 — 그건 모션이 한다.

   **2a — 프레임이 회전 사슬로 도달 가능할 때** (`world_xy`, 유리수 degree 회전들).
   `SketchPlane` 이 출처(모션 핸들)를 들면 끝이고 **새 `Motion` 변종이 필요 없다.**
   위험 없는 순이득이지만, 오늘 f64 경로가 틀린 답을 내고 있는 것은 아니므로 **급하지 않다.**

   ★★★ **2b 는 채택됐다** — 무리수 계수를 f64 로 들어올리는 대안이 기각됐기 때문이다
   (§「구현이 막힐 수 있는 자리」 1). 기울어진 면 위의 스케치를 정확히 다루는 **유일한 길**이므로
   *"아플 때 열면 된다"* 가 아니라 **설계의 일부**다.

   **2b — 도달 불가능한 프레임.** ★ 흔한 예가 **프리즘의 옆벽**이다: 프로파일의 변이 `(1, 2)` 면
   옆벽 법선이 `(2, −1, 0)` 이고, X 축을 거기로 돌리는 각이 `atan(1/2)` 라 유리수 degree 가 아니다.
   그때는 프레임을 정의로 든다:

   ```rust
   SketchPlane { plane: Handle<Surface>, origin: [Rat; 3], ref_dir: [Rat; 3] }
   // 실현: w = n/|n| ,  u = (ref_dir − (ref_dir·w)w)/|…| ,  v = w × u
   // 프로파일의 변들이 이 프레임 안에서 유리수 계수의 벽 평면이 되고, 그 평면들이 프레임 모션을 든다
   ```

   `ref_dir` 는 **유도하지 않고 저장한다**(유도 규칙을 바꾸면 모든 스케치가 조용히 돌아간다).
   `ref_dir × normal != 0` 은 유리수 외적으로 정확히 검사한다.
   (같은 패턴이 이미 있다: `nacre_geom::Cylinder` 의 `ref_dir`.)
   `Motion` 이 `nacre-scalar` 에 살면 `Handle<Surface>` 를 못 쓰므로 모션 노드에는 법선을 인라인해야
   하는데, **유리수라 등식으로 정확히 검사되므로** (W) 같은 위험은 없다.

   ★ **대가**: `Motion` 이 축 정렬 밖으로 나가면 그 전제 위에 선 지름길들(`Axis::plane`, 축별 오차,
   `shared_base`, 미러 패리티, *"90°계열은 tol 0"*)을 3×3 일반형으로 다시 써야 한다.

   ★★ **대가는 지름길이지 정확성이 아니다.** 실현 통로(`realize`)는 이미 무리수를 다룬다 —
   `Rotate` 의 `cos30 = √3/2` 가 그렇다. 프레임 모션은 *유리수의 `√`* 로 같은 통로를 탄다.
   ⇒ **막히는 위험이 아니라 다시 쓸 분량의 문제다.** 근거는 §「구현이 막힐 수 있는 자리」 1.

   ★ **2a 는 여전히 옵션이다** — 위험 없는 순이득이지만, 2b 가 2a 의 경우를 포함하므로
   (`ref_dir` 로 축 정렬 프레임도 적힌다) 2b 를 먼저 세우면 2a 는 특수화로 흡수될 수 있다.
   **하나로 갈 수 있는지는 구현 시 정한다.**

3. **통일안을 채택했다 — 남는 전제와 비용.**
   점의 표현을 하나로 두면서(`Vertex` 가 세 평면만 든다) 열거형과 `WorkingExplicitPoint` 가 사라졌다.
   층 구조(정의 + 두 실현)는 **평면 한 곳에만** 남았다. 남는 것은 둘이다.

   ★ **전제 — 공선 정점을 만들지 않을 것.** 프로파일에 공선 점이 있으면 양옆 벽이 **같은 평면**이 되어
   `[S, S, S_cap]` — 평면이 둘뿐이라 교차가 **직선**이고 점이 정해지지 않는다.
   그런 정점은 **인접 면이 둘**이라 애초에 2-manifold 정점이 아니다(꺾이지 않는 모서리 위의 퇴화
   부산물이고, `unify_coplanar_faces` 가 하는 일이 정확히 그런 공면 면을 합치는 것이다).
   ⇒ *"표현할 수 없다"* 가 아니라 **"만들지 말아야 한다"** 이고, 프로파일 정리나 구성 직후 병합으로 닫힌다.
   ★★ interning 덕분에 탐지가 **`s[i] == s[j]` 한 번**이다.

   ★ **비용 — 좌표 캐시의 정확도.** 유리수 → f64 는 반-ulp 였는데, 세 평면 풀기는 나눗셈이 들어간다
   (축 정렬이면 정확). **캐시 이야기**라 판정에는 영향이 없고, 좌표가 결과인 STEP 출력은
   「실현 통로는 하나다」의 `realize(p, 128) → round_to_f64` 로 **정확 반올림**해 낸다.
   ⇒ 실질적으로 닫혀 있고, 남는 것은 **표시·테셀레이션이 그 f64 로 충분한가**뿐이다(충분해 보인다).

4. **정의의 재지시** — 거의 닫혔다.
   솔리드를 옮길 때 정점의 정의(`surfaces: [Handle; 3]`)를 새 면 핸들로 다시 가리켜야 하는데,
   오늘 `transform_solid` 는 **그 솔리드의 면들**만 훑어 새 surface 를 만든다. 정의가 면으로는
   안 쓰이는 평면을 가리키면 옮길 새 핸들이 없어 `origins_are_remappable` 이 **거절**한다.
   ★ 아레나는 지우지 않으므로 **가리키는 대상이 사라지는 일은 없다** — 문제는 *"이번 변환이 그
   평면의 이동본을 만들었나"* 뿐이다. ⇒ **정의가 가리키는 평면도 함께 이동시키면** 재지시가
   구성상 언제나 성공하고, 게이트도 우회로(`Moved{base,motion}`)도 필요 없어진다.
   남는 것: 그렇게 만들어진 평면은 어떤 면도 쓰지 않으므로, **순회·직렬화가 정의를 따라가야** 한다
   (오늘 `Model::reachable` 은 면을 통해서만 돈다).

5. **곡면(M6)이 오면 무엇이 바뀌나 — 둘이고, 둘째가 크다.**

   **(a) 곡면의 진실 모양.** 평면이 `[Rat; 4] + motion` 이듯 원통도 유리수로 적힐 것으로 본다:
   `{ point: [Rat;3], dir: [Rat;3], radius: Rat, ref_dir: [Rat;3], motion }`.
   `dir` 을 원시 정수 벡터로 정준화하면 평면처럼 interning 도 된다. 비교적 단순한 문제다.

   **(b) ★ 정의가 점을 지목하지 못하게 된다.**
   `Vertex { surfaces }` 가 **정의**로 성립하는 이유는 평면 셋이 만나는 점이
   **최대 하나**이기 때문이다(선형 연립). 이차곡면 셋은 Bézout 로 **최대 8점**에서 만난다 —
   원통 둘과 평면 하나가 두 점에서 만나는 식이다. 그러면 `[Handle; 3]` 은 *"어느 점"* 을 말하지 못한다.

   선택지: 가지 번호를 붙이거나(`branch: u8` — 번호가 **결정적**이어야 한다),
   *"두 곡면의 교차 곡선 위, 세 번째와의 k번째 교차"* 처럼 다시 이름 짓거나.
   판정 방법도 달라진다 — 평면 셋은 Cramer 로 풀리지만 이차곡면은 아니고,
   design.md 가 인용하는 **QI 3부작**(pencil 분류)이 그 자리다.

   ★ 지금 정할 일이 아니다. M6 에서 실제 형상을 만나야 어느 방식이 맞는지 안다.
   ★★ 통일안을 채택했으므로 이 문제는 **모든 점**에 걸린다 — M6 의 가장 큰 항목이다.
