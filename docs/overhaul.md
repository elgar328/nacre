# nacre 오버홀 — 완전한 M5: 유리수 표현 + 명시 공유 + TIP

## 0. 이 문서의 지위

M5까지(c-1~c-4) pad/pocket=boolean 통합과 비볼록 처리를 진전시켰으나, 커널이 **축정렬 전용**이라는 근본 한계가
남았다. 이 문서는 그 한계를 넘어 **회전(비정렬·마름모·각도 스케치)을 지원하는 실사용 M5**로 가는 오버홀의 비전과
결정을 기록한다. 사용자와의 공동설계 결과다.

**결정의 지위 구분:**
- **OCCT n0로 확정**(실측 완료): §8 다중 솔리드 출력·manifold 정책.
- **설계로 확정**(근거 명확): §4 유리수 표현, §5 명시 공유, §6 TIP 판정 정책, §7 op-log 소유·TNP 정책.
- **2D 실험으로 검증 완료(✅)**: 위 결정들이 실제로·실용적으로 도는지를 격리 2D 샌드박스가 실측했다
  (`experiments/exact2d/`, `FINDINGS.md`, 26 테스트). **다섯 가설(H1 유리수·각도 / H1.5 고정밀 삼각 / H4 TIP /
  H2/H3 명시 공유 / H5 op-log) 모두 성립.** 단 실측이 **두 가지를 교정**했다(아래 반영): **(a) 고정밀 층 = twofloat
  탈락 → `astro-float`**(H1.5), **(b) 회전 tol 새-오차 = 접선형 반증 → 좌표혼합 `(|x|+|y|)·da`**(H4-soundness).
  부수로 astro-float `cmp` 0-비교 버그(#44)·번들링 지수폭발(필수)도 실측. 3D 이식은 **GO**(빅뱅 아님 — 메커니즘
  이식 + 사이드카 점진 은퇴).

design.md와 무모순을 유지한다. 상충 시 이 문서가 "design.md §X 갱신"을 명시한다. 실제 3D 구현은 실험·본설계
이후의 별도 작업이며, 이 문서는 **방향과 결정의 기록**이다.

**★ "완벽히 정확"의 정직한 의미.** 이 오버홀이 목표하는 정확성은 **"위상 결정은 항상 정확(declare-0 조건은 커널이
추측 않고 사용자에게 확인, '같다'면 Handle 재사용으로 추이성 붕괴를 구조적 차단, 병합·별개 시나리오가 모두 무효면
정직히 거절 — §6), 무리수 영역(회전 좌표·독립 솔리드 교차점)의 좌표는 tol 이내 근사 + export 시 correctly-rounded
f64(§4)"**다. **유리수·참조-공유 영역에서는 좌표까지 exact**다. CAD 견고성에서 결정적인 것은 위상이므로 실사용상
강력하지만, "모든 좌표가 f64 한계까지 오차 없음"은 아니다 — 회전 boolean이 만든 교차 정점은 무리수라 exact 표현이
없다.

## 1. 동기 — 왜 오버홀인가

- **축정렬 전용은 실사용 M5가 아니다.** 일반 seam 경로는 회전을 "돌리긴" 하나 tol 추적이 없어 경계에서 조용히 틀릴
  수 있고, 공면-접촉 사이드카(pad/pocket/오버행)는 축정렬 전용이다.
- **가지치기는 수익 체감.** 남은 케이스(비볼록 Cut·비볼록 footprint 오버행 등)는 축정렬 하위 시스템의 구석이라
  실사용으로 이어지지 않는다.
- **목표**: 회전 지원 실사용 M5. 스케치를 임의 평면(회전 포함)에 그려 extrude·boolean 하고, 공면·접촉이 exact하게
  처리된다. **곡면은 여전히 M6+** 비목표.

## 2. DNA 재확인 (다섯 원칙, 그중 ③을 실현)

①정확 기하가 진실 ②append-only 단일 참조 Handle ③**연산 이력 보존(model = replay)** ④tess 출처태그 ⑤tol은
Discovered에만. **원칙 ③은 현재 유일하게 미구현**이다 — `Model`에 연산 로그가 없고 `apply`는 즉시모드라
"model=replay"가 aspirational이다(§7). 오버홀이 이를 **실현**한다. 나머지 원칙은 오버홀이 강화하되 어기지 않는다.

## 3. 중심 논지 — 판정을 exact 2D 프레임으로, TIP는 프레임-교차에만

회전 좌표는 무리수(cos/sin)라 exact 산술로 표현 못 한다. 그러나 오버홀의 두 장치가 **회전 문제를 대부분 exact
영역 안에 가둔다**:

- **참조-공면(§5)**: 면에 그린 스케치의 tool body 밑면은 그 면의 `Surface` Handle을 **공유**한다. boolean이 두 면이
  같은 Handle임을 O(1)로 보고 **즉시 공면-접촉**으로 처리 — 계산 0, 회전무관, seam은 Constructed(tol 0).
- **exact 2D 프레임**: 공면-접촉 재구성의 기하 판정(포함·crossing)은 대부분 **스케치의 2D 프레임 안** 문제다.
  스케치 2D 좌표가 유리수(exact)면 같은 프레임 안 orient2d는 **surface의 3D 회전과 무관하게 exact**.

⇒ **흔한 케이스(면 위 스케치→pad/pocket, 회전 포함)를 TIP 없이 exact**로 처리할 여지가 크다. **TIP가 정말 필요한
곳**은 프레임이 서로 다른 **독립 솔리드 간** 상호작용 — 우연한 공면(독립 회전 솔리드가 우연히 공면), 회전 솔리드
들의 **횡단 seam**. 오버홀은 "빅뱅 재작성"이 아니라 (a) 참조-공면+2D-프레임으로 흔한 회전 exact + (b) TIP는
독립-솔리드 교차에만, 으로 쪼개진다.

**★ 성패를 가르는 표현 결정(실험 대상):** 현재 정점은 3D-only(`Vertex.point`, UV 없음). "같은-surface 2D exact"를
얻으려면 **surface 위 정점에 exact 2D(UV, 유리수) 좌표**를 두는 표현이 필요할 수 있다(스케치 Constructed 정점의
UV = 스케치 원좌표, exact). 이 표현 채택 여부·비용은 실험이 판정한다.

**★ 커버리지 상한(정직).** "면 위 스케치→pad는 2D 프레임 안이라 exact"는 **단일 공유 프레임 안**에서만 참이다.
회전면 위 pad 결과에 **또 다른 회전면 위 pad**를 하면 두 접촉이 하나의 공유 2D 프레임 안이 아니어서 TIP 영역으로
넘어간다. 회전이 섞인 실제 모델링에서 exact 경로 비율이 기대보다 낮을 수 있다 — 설계 결함은 아니나 정직한 상한이며,
그만큼 TIP(§6)의 견고성·속도가 실사용 품질을 좌우한다.

## 4. 근본 표현 — 유리수 vs 무리수 (모든 스칼라 통일)

- **치수 = 유리수.** exact 일치 판별과 exact 해시의 토대. f64 오차 0.
- **각도 = 유리수, deg 단위.** 실제 회전 좌표는 f64(cos/sin 무리수)·판정은 double-double로 올리되, **각도 값 자체는
  유리수로 정확히 누적**한다. 작은 각을 반복 누적해 한 바퀴면 **정확히 360°**(예 36×10=360, 유리수). f64 각도면
  359.9999…로 드리프트해 스케치가 안 닫힌다. ⇒ **각도(유리수·정확 누적) ↔ 삼각 실현(무리수·f64 좌표/double-double
  판정)을 분리.** UV 좌표도 유리수.

**★ 유리수의 경계 규칙 — 유리수는 입력 표현이지 계산 매체가 아니다.** 유리수의 목적은 **입력단에서 사용자 의도가 f64
오차로 왜곡되지 않게** 하는 것이다: `1.1` 입력이 `11/10`으로 보존되어 `1.1 × 7`이 `7.7`과 **정확히** 같아야 한다
(얇은 막 문제의 근본 해결). 이를 boolean 좌표 산술까지 전파하면 design.md §3의 경고("**임의 정밀 유리수는 Newton
반복에 넣으면 비트가 폭발**")에 정면으로 걸린다. 그래서 경계를 못박는다:
- **입력단**: 치수·각도를 유리수로 받는다(사용자 의도의 exact 보존).
- **유리수 + 유리수** (`+·−·×`, 축정렬 오프셋, 유리수-평면 교차): **유리수로 계산**해 exact를 유지한다.
- **불리언 등 복잡 연산의 좌표 생성**: **f64로 강등**한다. 유리수를 좌표로 **전파하지 않는다**(비트 폭발 차단).
- **정밀 판정이 필요한 자리**: **double-double로 상승**(§6 TIP).
- **뉴턴법 등 수치 반복**: f64/double-double(유리수 표현 불가).
- **혼합**(유리수 + 이미 f64/dd가 된 값): **f64/dd로 강등**해 계산.
- **연산 중 오버플로/비트 임계 초과**: 유리수끼리의 `+`라도 분모가 서로소인 값이 반복 유입되면 분자·분모 비트가
  커져 오버플로(또는 BigInt 무제한 성장)가 날 수 있다. **죽지 말고 f64/double-double로 전환해 계산을 이어간다. 정의는
  그대로.**

**★★ "강등"의 의미 — 정의를 버리는 게 아니라 캐시를 f64/dd로 계산하는 것.** 강등은 **연산 수행 시 f64/dd로 계산한다**는
뜻이지, **입력 정의를 f64로 덮어쓴다**는 뜻이 아니다. 이 구분이 export 불변식(위 2번 위험)과 판정 결정성(3번 위험)을
동시에 지킨다:
```
정의 (불변, 항상 보존):
  점 = "입력A + 입력B + …"(연산 이력);  입력A = 11/10(유리수 그대로)
캐시 (가변):
  평소          → 유리수로 계산(exact, tol 0)
  비트 임계 초과 → f64/dd로 계산(tol 발생, Origin에 기록)
  export 시      → 정의로부터 고정밀 재계산(exact 복원)
```
- **export 불변식 유지**: 사용자 입력 유리수는 언제나 보존되므로, 강등은 **연산 결과 캐시**만 f64/dd로 내리고 export
  때 정의로부터 다시 exact 재계산할 수 있다. "누적 f64가 유일한 진실"이 되는 점은 없다.
- **★ 강등은 캐시 결정이지 판정 결정이 아니다(3번 해소)**: 판정을 **"캐시 상태"가 아니라 "점 정의"의 함수**로 두면,
  강등이 언제 발화했든(경로마다 달라도) 같은 점 정의에 대한 판정은 **같다** — 강등이 새로운 경로-의존 tol 원천이
  되지 않는다. (§6 결정성 요건·§11 H4-consistency와 한 몸.)
- **표현 선택(i128 vs BigInt)·강등 임계는 H1이 실측해 정한다**(연쇄 불리언에서 분모가 실제로 얼마나 커지는지,
  i128로 충분한지, 트리거를 어디 둘지).

즉 유리수는 **입력과 유리수-순수 파생**에만 살고, 무리수·반복·복잡 연산이 닿거나 **비트 상한을 넘는 순간** 캐시가
f64/dd로 내려간다(정의는 불변). 이 규칙이 비트 폭발과 성능 부담을 동시에 해소하며 design.md §3의 정밀도 분업과
정합한다.

**★ tol 모델의 올바른 기준 = "유리수냐 무리수냐"(직선/회전 아님).** §TIP의 암묵 가정("직선=거리는 tol 0, 회전=각도만
tol")은 **v1에서만 참**이다 — 거리도 각도와 **똑같은 두 출처**를 갖는다: 사용자 입력→유리수→tol 0 vs 유도값→무리수
→tol>0("두 점 사이 거리만큼 이동" √(...), 회전으로 생긴 엣지 길이, 스케치 **구속 솔버**의 해). 그래서 통일한다 —
**모든 스칼라(거리·각도·좌표) = 값 + tol**:
- **tol = 0 : 유리수** (사용자 입력, 유리수끼리 `+`·`−`·`×`).
- **tol > 0 : 무리수** (`√`·`cos`·`sin`·구속 솔버 해에서 유도) + 그 값의 이산화 오차 + 입력 tol 전파.

효과: **v1 현재** — 거리·각도가 전부 사용자 입력(유리수)이라 tol 0, 회전 좌표만 무리수 → **지금 설계와 결과 동일**.
**v1 이후** — 구속 솔버·유도 치수가 들어와도 **같은 모델로 자동 처리**, 수식 재유도 불필요.

**★ 수식 구현 지침**: v1에서 각도·거리가 유리수라 그 tol 항이 0이더라도, **tol 공식에서 "각도 tol"·"거리 tol" 항을
삭제하지 말고 0으로 둔다.** 유도된 무리수 스칼라(구속 솔버 해·√ 거리)가 들어오면 그 항이 0이 아니게 되며, 미리
지워두면 그때 공식을 재유도해야 한다. 즉 v1 회전 자체-tol = 삼각 실현 오차 + 이산화 오차 (**각도 오차 항 = 0**,
그러나 항은 존재).

**§TIP "직선 구간은 fraction 강체로 묶는다"의 재해석·일반화(= design.md §TIP 6·7·8 갱신):** "직선이라서" tol 0이
아니라 **"유리수라서" tol 0**이다. 그리고 **강체 묶기는 직선에 국한되지 않는다 — 같은 종류의 유리수 연산 run은 모두
묶인다**:
- **연속 유리수 이동**: 위치를 유리수로 합산 → 그 구간 오차 0.
- **같은 축의 연속 유리수-각도 회전**: 각도를 유리수로 합산해 **누적 각을 한 번만 cos/sin 실현** → 회전마다 이산화가
  붙지 않고 그 run 전체가 이산화 1회. (2D는 회전이 모두 한 축[z]이라 유리수-각도 회전이 **항상 묶인다**. 3D는
  **같은 축만** 묶이고 축이 바뀌면 합성이 무리수-각도가 되어 **경계**다.)
  **★ 번들링은 최적화가 아니라 필수(H4-amplification 실측).** 만약 묶지 않고 **증분 실현**하면, 전파 항 `|R|`(성분별
  절댓값 행렬)의 행합 `|cos|+|sin| ≥ 1`이 매 스텝 곱해져 **tol 바운드가 지수 폭발**한다(실측: 30스텝에 실제 오차의
  ~20만 배; 실제 오차는 회전 `R`이 노름 보존이라 평평). 누적각 1회 실현이 이 폭발을 원천 차단한다. (폭발해도 tol은
  **sound 최악-보장**이라 조용히 안 틀리고 상승/거절로만 감 — §6·§TIP 8. 확률적(RSS) tightening은 보장이 아니라
  안 씀.)

두 경우 모두 그 run의 연산·이산화 오차 0이고, **무리수로 실현되는 경계에서만** tol 1회 발생 — 직선 run이 회전을
만나는 지점, 회전 run의 누적 각을 cos/sin으로 실현하는 지점, 3D 축 변경, **유도된 무리수**(√ 거리·구속 솔버 해).
그런 무리수가 섞이면 그 구간은 fraction으로 못 묶는다. design.md §TIP가 각도를 f64로 뒀다면 **유리수-deg로 교정**.

이것이 exact 공유·정확 각도누적·TIP의 tol=0의 **공통 토대**(유리수 run은 강체로 묶여 오차 0, 무리수 실현 지점에서만
tol 발생).

**★ export 불변식 (부수 페이오프):** 어떤 점도 "누적 f64가 유일한 진실"이 되면 안 된다 — 항상 exact 정의를 보유
(유리수/회전이력/세-평면). 그러면 STEP export 전 **전 모델을 고정밀 재계산 → 최근접 f64 반올림**으로 각 좌표가
correctly-rounded f64(0.5 ULP)가 되어 인터랙티브 누적 드리프트가 씻긴다(STEP 정밀도 "f64 표현 한계까지"). 특별
훅 불요 — 캐시 최대정밀 재생성(= op-log 고정밀 replay)일 뿐. 오버홀이 정의-진실을 지키면 공짜로 따라온다.

## 5. 명시 공유 (요소 공유) — surface → 엣지 → 정점

**원리:** 새 구성이 기존 요소와 같으면 새로 만들지 않고 **기존 Handle을 공유**한다(append-only 단일 참조를 스케치·
부울까지 관철). 공유는 3층: surface(공면 인식)·엣지·정점.

**★ (b) 명시 공유로 확정 — 전역 자동병합 폐기.** 공유는 **문맥상 같은 점·평면일 때만** 생긴다:
- **공유하는 것(참조·명시적)**: 면에 스케치 → 그 면 `Surface` Handle 재사용; 스케치 내부에서 경로가 닫힘; **불리언이
  실제 교차·접촉을 계산해 만든 공유**(OCCT 방식).
- **공유하지 않는 것**: 다른 경로로 만들어진 두 요소가 **우연히 같은 좌표**에 오는 경우. 별개로 유지하고, 불리언
  시점에 그 자리에서 판정한다.

**결정적 근거 — 전역 좌표-해시 자동병합은 TNP 정책과 근본 충돌한다.** 파라메트릭 편집에서 치수를 바꾸면 우연히
겹치던 두 점이 안 겹치거나 그 반대가 된다 → **치수 변경이 위상을 바꾼다**. 그러나 확정된 TNP 정책(§7)은 "치수만
변경(위상 불변) → 자동 replay"다. 전역 자동병합은 그 정책을 깬다. (부수적으로, 의도적으로 별개인 두 부품을 같은
위치에 두면 떼어낼 수 없게 되는 문제도 피한다.)

**부수효과 — "exact 상등 증명 불가" 근본 한계를 대부분 우회한다.** 생성 시점에 "이 점이 기존 점과 같은가?"를 아예
묻지 않으므로 **회전 좌표의 exact 비교가 불필요**하다. 판정이 필요한 자리가 "모든 점 생성"에서 "**불리언 교차 지점**"
으로 축소되고, 그것은 §TIP가 담당하기로 한 영역(우연한 공면, 회전 솔리드 횡단 seam)과 정확히 일치한다.

**스케치 모델과 참조-공면은 같은 메커니즘이다.** "면에 스케치를 그린다" = 그 면의 `Surface` Handle을 재사용한다
(imprint가 이미 하는 패턴). pad하면 프리즘 밑면도 그 surface를 공유하므로, boolean이 O(1)로 공면-접촉을 처리한다.
스케치가 면 경계와 정점·엣지까지 (스냅으로) 공유하면, pad의 접촉이 참조로 이미 공유돼 **seam이 계산 0·Constructed**.

## 6. TIP — 판정 정책 (술어 vs TIP 역할 분리)

- **술어(indirect predicates)**: 주어진 좌표로 행렬식을 계산해 항상 +/−/0을 확정 반환한다. 내부 정밀도 상승
  (f64 필터 → `Expansion`)은 **행렬식 계산의 정밀도**를 올리는 것이지 입력 좌표를 바꾸는 것이 아니다. 좌표가 회전인지
  유리수인지 술어는 모른다.
- **TIP**: 좌표를 만들고(회전은 f64 → 애매하면 double-double 재계산)·좌표의 tol을 추적하며·**술어의 답을 믿을지
  판단**한다. **술어가 +/−를 반환해도 TIP가 "못 믿겠다"고 할 수 있다** — 술어가 계산한 행렬식 값이 좌표 tol에서 유도한
  오차 한계보다 작으면 부호가 좌표 오차에 묻혀 뒤집힐 수 있다(예: det 1e-35 < 오차 한계 1e-29 → 술어는 "+"라도 진짜
  "−"일 수 있음). 그대로 받으면 조용히 틀린다.

**tol 표현(확정 — H4-soundness 실측 교정):** 모든 tol(회전·직선·이산화)은 **xyz 방향별 벡터**로 표현·누적한다
(스칼라 tol 탈락 — z축 둘레 회전이면 z 방향 오차 0인데 스칼라는 모든 방향에 실어 불필요한 상승을 유발). 회전 tol은
**세 항**의 합이다:
```
새 tol = |R|·(기존 tol)            [b: 전파 — 기존 tol 벡터의 방향을 회전]
       + (|x| + |y|)·da_이산화      [a: 새 오차 — 실현 반올림, 좌표 혼합]  ★ H4 교정
       + da_각도 × 모멘트암          [c: 각도 불확실성, 접선 — v1엔 0]
```
- **(b) `|R|·(기존 tol)`** — 기존 tol의 **방향을 회전**(성분별 절댓값 행렬 × 벡터; x-tol이 z축 90° 회전 후 y로 옮겨감 —
  안 하면 상한 깨짐). 직선 이동도 새 오차는 안 만들지만 이 앞선 tol을 싣고 간다. **실측(H4-soundness piece 2)**: 증분
  회전 체인 5000회 0 붕괴(sound). **필요성은 비대칭 tol에서** — v1의 대칭 (a)-tol만이면 전파를 빼도 margin에 흡수돼
  안 깨지나, x에 몰린 tol을 90° 회전하면 오차가 y로 옮겨가 전파 없으면 tol_y=0으로 과소예측(v1-후 √거리·솔버).
- **★ (a) `(|x| + |y|)·da_이산화`(새 오차 — H4-soundness가 교정)** — 회전 좌표를 유한 정밀도로 실현할 때의 반올림
  오차. cos/sin을 **독립 반올림**하면 순수 회전이 아니라 **방사 성분**이 생겨(`err_x = |x·δc − y·δs|`), 옛 접선형
  `da × 모멘트암`은 좌표 하나가 0 근처일 때 그 성분을 **과소평가**해 상한이 깨진다. 성분별 tol은 **두 좌표를 합친**
  `(|x|+|y|)·da`여야 sound(0으로 안 꺼짐). `da_이산화` = 실현 반올림 한계(f64 ~16 ulp; astro-float 상승 시 ~2^-P).
  **실측(H4-soundness, 10000 랜덤)**: 접선형은 220회 과소평가(unsound), 좌표혼합은 0회·최악 ~3.5× 이내 보수(타이트).
- **(c) `da_각도 × 모멘트암`(접선)** — **각도 자체의 불확실성**(구속 솔버 해·비유리수 각). v1은 유리수 각이라 `da_각도=0`
  (그리고 (a)의 여유가 f64 각도-반올림까지 흡수). **v1-후**(유도 치수)에 살아난다 — **항은 지우지 말고 0으로 둔다**(§4).

합성 = 성분별 절댓값 합. 판정 시 각 방향 tol이 행렬식에서 자기 계수로 증폭돼 오차 한계를 이룬다. (더 조이려면 좌표를
고정밀 실현 후 1회 반올림해 `tol = ulp(좌표) = 2^-P·|좌표|`(좌표정렬·더 타이트)로 둘 수도 있으나, f64-직접 실현보다
느리다 — 필터엔 (a)의 좌표혼합, 상승엔 좌표정렬.)

**판정 정책(확정):**
1. f64 좌표로 술어 판정 → tol(방향별)로 오차 한계 계산 → `|det| > 오차 한계`면 채택.
2. 애매하면 → **정밀도를 올리며(astro-float, dial 가능) 회전 좌표 재실현·재판정**. 참값이 nonzero면 어느 정밀도에서 부호가
   확정된다("진짜 다른데 가까운" 경우는 여기서 해결 — 질문 불필요).
3. **정밀도 상한(멈춤 규칙)까지 올려도 애매하면 → `declare-0 조건`**(같음/공면/공선일 수 있으나 유한 정밀도로 확정 불가).
   상한이 필요한 이유: 무한히 올릴 수 없고(비용), **초월수의 exact 0/상등은 어차피 유한 정밀도로 증명 불가**. **여기서
   커널은 "같다"고 추측하지 않는다** — 추측이 추이성 붕괴·공면-vs-측면 모순의 근원이다(아래 ★★). 대신 사용자에게
   확인받는다(정책 §6-아래). (회전(각도) 유래 애매함의 irreducible 핵은 이 상한에서 남아 질문으로 넘어간다.)

**근거:** 초월수(cos/sin)의 exact 상등은 유한 정밀도로 증명 불가하므로 어딘가에서 판단이 필요하고, 고정밀 상승 층의
tol은 상용 CAD tolerance(~1e-9)보다 압도적으로 작아 그 스케일에서만 발동한다. **★ 이 상승 층은 `astro-float`(임의정밀)
로 확정됐다(H1.5 — twofloat 삼각 부정확으로 탈락; design.md §TIP 6). 이하 문서의 "double-double"은 이 층의 일반명이며,
정밀도가 dial 가능이라 declare-0 조건은 "고정밀으로도 애매"로 읽는다.** **판단의 주체가 커널의
추측이 아니라 사용자의 의도**라는 점이 핵심이다(TNP "마법 재추론 금지"와 같은 철학). (tol 전파 수식·강체 묶기는
design.md §TIP; 그 공식의 상한성·속도는 실험 H4가 검증.)

**★ 결정성 요건(함정 — §11 열린 질문).** 판정(술어 부호·declare-0 조건 감지)은 **경로-독립적으로 결정적**이어야 한다 —
같은 기하 질문은 계산 경로·정밀도 상승 이력·캐시 유무·판정 시점 tol과 무관하게 **항상 같은 답**을 내야 한다. 결정성을
보장하는 규칙은 **판정을 좌표 캐시 상태가 아니라 "점 정의"의 함수로 두는 것**(§4 강등이 판정을 바꾸지 않는 근거) —
§11의 열린 질문이며 실험 H4가 일관성을 실측한다.

**★★ 전역 상호일관성 — 진짜 위험, 그리고 그 해소(커널이 추측하지 않는다).** exact 술어가 견고한 이유는 "입력이 exact면
어떤 일관된 선택도 전역적으로 실현 가능한 기하에 대응"하기 때문인데, **커널이 "가까우니 같겠지"라고 추측**하면 그
추측이 서로 모순될 수 있다(tolerance 기반 상등은 추이성이 없다 — 거리는 추이적이지 않다). 붕괴 예:
- **추이성 붕괴**: 임계 `1e-30`에서 A=0·B=6e-31·C=1.2e-30이면 커널이 "A==B"·"B==C"라 추측하나 `|A−C|>tol`→"A≠C".
- **공면-vs-측면 붕괴**: 정점 V를 면 F에 추측으로 공면 붙였는데 다른 경로 재계산이 "F 위쪽(+)"을 내면 → 자기교차.

근본 원인은 **커널이 사용자 의도를 추측**한 것이다. 두 요소가 1e-30 안에서 가까운 게 의도인지 우연인지는 **사용자만
안다.**

**★ 두 해법을 모두 배격한다.** (a) **전역 스냅 라운딩** — 좌표를 격자에 뭉개는 전역 tolerance라 원칙 ①·⑤를 정면
위반하고 (5d)의 tolerance 은퇴를 되돌린다. (b) **커널이 declare-0을 스스로 판단**(추측) — 위 붕괴의 근원. **어느
쪽도 채택하지 않는다.**

**⇒ 확정 정책 — 커널이 추측하지 않고 사용자에게 확인받는다.** declare-0 조건이 감지되면(2에서 double-double로도
애매), 커널이 "같다/다르다"를 정하지 않고 **의도를 확인**한다. 1e-30 스케일에서만 발동하므로 극히 드물어 사용자를
방해하지 않는다.

**★★ 질문 ⟺ 기하적 애매함(일치 여부가 아니다).** 정확히 일치하면 — **문맥상이든 우연이든** — exact 술어가 "같다"를
증명하므로 **묻지 않는다**(원칙 ①: 정확 기하가 진실). 세 경우로 갈린다:
- **① 문맥상 동일**(면에 프로파일 그려 pad): 생성 시 **Surface Handle 공유**(§5 참조). 질문 없음.
- **② 우연한 정확 일치**(다른 두 경로가 우연히 같은 exact 좌표): **생성 시 병합하지 않는다**(§5 — 별개 Handle 유지).
  자동 병합하면 나중에 치수를 바꿔 둘이 안 겹칠 때 **치수 변경이 위상을 바꿔** TNP 정책(§7)이 깨진다. 그 둘 사이에
  **불리언이 실제로 일어날 때만** 불리언이 exact 접촉을 계산해 경계를 공유한다(§5 "불리언이 만든 공유", §8-3 — 전역
  자동병합 아님). 질문 없음(정확이라 애매 없음).
- **③ 애매한 일치**(1e-30, 회전 등): 기하가 확정 불가 → **declare-0 → ask**(위 정책).

즉 물음은 오직 ③에서만. ①·②는 정확이라 결정적으로 처리하고, 병합 여부는 **§5의 문맥 규칙**(참조=공유·우연=생성 시
별개·불리언 접촉 시 공유)이 정한다.

- **★ "같다"면 새 점을 만들지 않고 기존 요소를 재사용(Handle 공유) → 추이성 붕괴가 구조적으로 불가능**:
  ```
  A~B → 사용자 "같다" → B를 버리고 B 참조처가 전부 A를 참조 → B라는 점이 존재하지 않음(B ≡ A, 동일 Handle)
    → 이후 "B vs C" 질문 자체가 존재 불가. 그것은 "A vs C"다. |A−C|>tol이면 그냥 "다르다"(declare-0 미발동)
  ⇒ "A==B, B==C, A≠C"라는 상태를 표현할 수가 없다.
  ```
  동일성이 **"가까움(계산)"이 아니라 "같은 참조(정의)"**가 되므로 추이성이 공짜로 성립한다. 이는 §5 명시 공유
  메커니즘이며 OCCT도 같은 방식(불리언이 접촉 엣지를 공유). **앞선 "추이성 검증 게이트"는 불필요 — 삭제.**
  **★ 이 메커니즘은 §5의 3층 모두에 적용된다(점만이 아니다).** declare-0 조건은 점 일치(성분별 박스)뿐 아니라
  **orientation 애매**(공선·공면; det 기반)도 포함하며, "Merge" = **그 층의 Handle 재사용**이다 — 우연한 공면(§3)이면
  **Surface Handle**, 공선·접촉 엣지면 **Edge Handle**, 점 일치면 **Vertex Handle**. 즉 §3이 지목한 "독립 회전 솔리드의
  우연한 공면"도 같은 ask→재사용으로 처리되어 별도 경로가 없다.

- **★ 질문 입도 = 최대 entailed 일치 그룹(하위는 자동 전파, 하나씩 안 묻는다).** `site = {A 정의, B 정의}` 쌍을 순진하게
  열거하면 두 동일 사각형이 겹칠 때 면1+엣지4+정점4 = **9쌍 → 9번** 묻게 된다. 그러면 안 된다. **가장 거친 레벨에서
  한 번만** 묻는다 — "이 두 **면**이 같은가?" 하나. "같다"면 그 면의 경계(엣지·정점)는 **구조적 대응으로 자동 병합**
  된다(추측이 아니라 **entailment** — 면이 같다면 그 사각형의 모서리·꼭짓점은 정의상 따라온다). 즉 **하나의 질문 =
  하나의 최대 entailed 일치 그룹**이고, 로그도 그 그룹 단위로 답을 기록한다(하위 쌍마다가 아니라).
  - **정확히 일치**하면 애초에 declare-0이 아니라 exact라 **질문 0개**(§5 참조 공유/exact 술어).
  - **전파 조건**: 하위가 **1:1 대응**될 때만. 경계가 실제로 다르면(부분 겹침·꼭짓점 수 불일치) 면-레벨 답이 "같지
    않음"이고, boolean이 실제 경계 교차를 계산해 **거기서 생기는 소수의 사이트**만 남는다. 독립적 별개 접촉(§6 위
    "사이트마다 다른 의도")과 entailed 하위는 다르다 — 전자는 각각 묻고, 후자는 상위 1회로 함의된다.

- **★ 묻기 전에 먼저 검증한다(선택지가 실제 있을 때만 묻는다).** 사용자가 "같다"고 답했는데 거절당하면 "왜 물었냐"가
  된다. 순서를 뒤집는다:
  ```
  1. declare-0 조건 감지
  2. 두 시나리오의 **국소 델타를 검사**(boolean 전체 재완주 아님):
     (가) 병합 시 국소 유효?(면 정점이 그 평면 위·퇴화 엣지/면 없음·국소 manifold: 엣지당 면 2·정점 link 단일 순환)
     (나) 별개 유지 시 국소 유효?
  3. 둘 다 유효  → 사용자에게 물음(진짜 선택지)
     병합만 유효 → "합쳐야 유효합니다. 진행할까요?"(여전히 사용자 확인, 커널 추측 안 함)
     별개만 유효 → 경고 후 별개 진행(모르고 지나가지 않게)
     둘 다 무효  → `Unsupported`(물어볼 것 없음)
  ```
  **★ 검증은 국소(정점의 star)만.** declare-0은 boolean **구축 도중** 발생해 그 시점 전역 위상이 미완이라 **전역
  Euler를 계산할 수 없다** — 대신 그 정점을 쓰는 면·엣지의 **국소 manifold**만 본다. 병합 전이 유효했다면 전역
  불변식(Euler 등)은 국소 manifold가 유지되면 따라오므로 **따로 검사하지 않는다**. 그래서 전체 재계산 불요이고,
  declare-0이 드무니 비용도 드물다. 이로써
  "병합이 점의 다른 관계를 깰 수 있다"는 잔여도 사전에 걸러진다(공면-vs-측면 붕괴 포함 — 병합 후 위상 검증이 그것을
  잡는다). **★ 검증 술어의 자기참조성**: 유효성 검사("면 정점이 그 평면 위에 있나")도 기하 술어라 그 자체가 declare-0
  조건에 걸릴 수 있다 — 이때 **재귀적으로 다시 묻지 않고 보수적으로 처리**한다(병합 검증이면 "평면 위 아님"으로 =
  병합 무효 쪽). 안전측이고 무한 재귀를 막는다.

- **★ 정책은 사이트별, 기본값 `Reject`(전역 설정 금지).** 전역 설정은 100줄 전에 켠 `Merge`가 지금 연산을
  조용히 바꾸고, 로그에서 정책이 안 보여 원칙 ③(연산 self-contained)을 위반한다. **한 연산 안에 애매 사이트가 여럿일
  때 사용자가 사이트마다 다른 의도**를 가질 수 있으므로(사이트1=같음·사이트2=별개 부품·사이트3=애매), **블랭킷 정책은
  "다 같은 의도겠지"라는 커널의 추측** — declare-0을 사용자에게 묻기로 한 취지와 정면 충돌한다. 그래서 **사이트별로
  해소**한다.
  ```rust
  enum Coincidence { Reject, Merge, Separate, Ask }   // Ask는 GUI 전용: 사이트마다 물어 각 답을 확정해 로그에 기록
  model.cut(a, b)?;                          // 99.99% — 기본 Reject
  //   declare-0 발동 시 Error: "애매한 접촉. cut_with(a, b, …)로 의도를 명시하세요."
  model.cut_with(a, b, Coincidence::Merge)?; // 편의: 블랭킷 기본값 — "모든 사이트 Merge"
  ```
  - **API는 블랭킷 허용, 로그는 항상 사이트별.** `cut_with(a, b, Merge)`는 편의상 "이 연산의 모든 애매 사이트를
    Merge"지만, **apply 시점에 사이트별 항목으로 전개해 로그에 기록**한다(§7 c). GUI `Ask`는 **사이트마다 물어** 각
    답을 그대로 사이트별로 기록 → replay가 다시 안 묻는다(원칙 ③).
  - **★ 사이트 식별자 = 좌표가 아니라 정의(무순서 쌍).** `사이트 = {요소 A의 정의, 요소 B의 정의}`(예 `{"S1의
    P1∩P2∩P3", "S2의 Q1∩Q2∩Q3"}`) — "A와 B가 같은가?"는 A·B에 순서가 없으므로 **정의를 정준 정렬한 무순서 쌍**으로
    둔다(`(A,B)`와 `(B,A)`가 같은 id). 정의는 replay에서 결정적 재생성되므로 **발견 순서와 무관하게 매핑** — 좌표
    기반 식별의 경로 의존성을 원천 회피(§5 명시 공유와 같은 원리).
  - 병합이 실제로 일어나면 리포트에 남긴다("N개 요소 병합됨") — 조용히 안 넘어간다. **범위는 좁다**: pad/pocket은
    surface Handle 공유라 declare-0이 거의 미발동, 실무 사이트 수는 **거의 항상 0~1개**(1e-30이라 다중 사이트는
    희귀²), 실제 쓰임은 **독립 솔리드 간 불리언**뿐 — 사이트별 구조 비용은 작고, 얻는 것(의도의 정확한 표현)은 크다.

- **★ 일치 declare-0 술어 = 성분별 박스(4번 해소).** "두 점이 declare-0 조건인가"(= 물어볼지 판단)를 방향별 벡터
  tol로 판정한다:
  ```
  X ≈ A  ⟺  |Xx−Ax| ≤ (tol_X.x + tol_A.x)  AND  |Xy−Ay| ≤ (…y)  AND  |Xz−Az| ≤ (…z)
  ```
  두 점 tol을 **합산**(둘 다 흔들림). 방향별 tol의 취지가 "각 방향 오차가 독립"이므로 판정도 성분별 독립이어야
  일관되고, **박스는 타원체보다 커서 안전측**(물어봐야 할 것을 놓치지 않음)이며 간단·빠르다.

- **잔여(정직 기록)**: (a) **연쇄 병합 변위** — 사용자가 A~B, B~C를 순차 승인하면 C가 tol보다 큰 거리(예 1.2×tol)
  이동할 수 있다. **위상 모순은 없고**(전부 한 점, 동치 성립) 매번 사용자 승인이며 변위가 1e-30 스케일이라 물리적
  무의미. (b) **비인터랙티브 모드** — 스크립트는 `Ask` 불가라 기본 `Reject`, 발동 시 에러로 정책 명시 요구. (→ §11-B 9)
  (c) **`Separate`의 내재적 퇴화** — 1e-30 떨어진 두 점을 별개로 두면 1e-30 두께 슬리버가 생겨 "퇴화 엣지/면 없음"
  검증에서 거의 항상 탈락한다(설계 결함 아님 — 검증이 잡음). "Separate가 실무에서 얼마나 실현되나"는 정직한 단서로
  남긴다(→ §11-B 10). (d) **사이트 비독립성** — 한 boolean 안에서 병합이 연쇄를 일으켜(잔여 a) **원래 없던 새 declare-0
  사이트를 만들 수 있다.** 그러므로 로그는 "처음 만난 집합"이 아니라 **연쇄로 유발된 사이트까지 전부** 담아야 replay가
  재현되고, 사이트별 독립 검증은 원칙적으로 **순차 적용·결합 무효**(각각은 병합 가능하나 둘 다 병합하면 퇴화)를
  고려해야 한다. 실무 사이트 수가 거의 0~1개(희귀²)라 이론적이나 정직히 남긴다(→ §11-A 7-v).

## 7. 연산 로그 / 타입 시스템

- **현재**: `Model`에 op-log 없음(apply 즉시모드; `replay`는 호출자 슬라이스 폴드). "model=replay"는 aspirational
  (원칙 ③ 유일 미구현). Operation은 `Handle` 참조이나 provenance 참조는 없음.
- **결정 (a) 소유**: **`Document`(파사드 `nacre` 크레이트)가 `Vec<Operation>`(로그=진실) + 파생 `Model`(replay 결과·
  live 상태)을 소유**한다. 원칙 ③ 실현·undo/redo·참조 replay-안정의 토대. `Model`은 로그를 일부러 배제하므로 소유자는
  상위 `Document`.
- **결정 (b) sugar 기록**: 로그는 `PadOnFace{face, profile, dist}` 같은 **sugar를 그대로 기록**(피처 트리). apply는
  내부적으로 extrude+Fuse로 desugar하되 로그엔 의도가 보존된다. desugar를 기록하면 "이건 패드다"가 소실돼 로그가
  피처 트리 역할을 못 한다.
- **결정 (c) 일치 정책은 사이트별로 연산에 기록(§6 확정)**: 각 연산이 declare-0 사이트별 해소를 **필드로 담아**
  self-contained하게 기록한다 — `Cut{a, b, coincidences: [(site_id, Merge), (site_id, Separate), …]}`. `site_id =
  {요소 A의 정의, 요소 B의 정의}`(정준 정렬한 **무순서 쌍**)로 replay에서 결정적 재생성·매핑(§6). **★ 사이트는 최대
  entailed 그룹 단위**(§6): 동일 면 일치는 면 1건으로 기록하고 경계 엣지·정점은 구조적 전파라 **하위 쌍을 따로 안
  기록**한다(9쌍이 아니라 1건). API의 블랭킷 기본값(`cut_with(…, Merge)`)은
  **apply 시점에 사이트별 항목으로 전개**해 기록하므로, 로그는 언제나 사이트별이다. 전역 설정 금지 — 로그만 보면 각
  사이트가 어떤 의도로 해소됐는지 드러난다(원칙 ③). GUI `Ask`는 **사이트마다 물어** 각 답을 `Merge`/`Separate`로
  확정해 기록하므로 replay가 다시 묻지 않는다(결정적 replay 유지).
- **TNP 정책(확정 — 정직한 해법)**: 편집은 v1 비목표(§0-3)라 현재 TNP 미발생(결정적 replay만). **편집을 열 때**:
  **치수만 변경(위상 불변) → 자동 replay**(참조 유효); **위상 변화 → 커널이 깨짐을 감지해 사용자가 수동 재지정**
  (마법 재추론 금지 — FreeCAD 실패의 교훈). 이 정책이 **의미론적 provenance**를 뒷받침한다 — raw `Handle<Face>`는
  치수 편집에도 취약하나, "어느 연산의 어느 프로파일 엣지/면 유래"인 의미론적 계보는 치수를 견디고 위상 변화를
  감지한다. **편집 구현은 후속 마일스톤**이나, provenance 타입을 지금 **계보로 확장 가능한 형태**로 남긴다(raw
  Handle로 박으면 편집 열 때 전면 재설계). (로그의 `Handle<Face>` 참조와 `Surface::FromFace`는 같은 replay-안정·
  편집-취약 패턴이므로 함께 다룬다.)

## 8. 불리언 출력 — 다중 솔리드 (OCCT n0로 확정)

**실측(Homebrew OCCT DRAWEXE):** 두 케이스 모두 결과가 **COMPOUND of 2 SOLIDs·checkshape valid·STEP 2×
`MANIFOLD_SOLID_BREP`(non-manifold 엔티티 0)**:
- **엣지 접촉 Fuse**(A=`[0,1]³`, B=`[1,2]×[0,1]×[1,2]`, x=1·z=1 직선만 만남): SOLID 2, V14(=16−2)·E23(=24−1)
  → 접촉 엣지+2정점 공유, 각 솔리드는 깨끗한 manifold 박스(E12·F6).
- **절단 Cut**(막대를 관통 박스로 두 동강): SOLID 2, V16·E24(완전 분리). nacre가 지금 `DISCONNECTED_RESULT`로
  거절하는 케이스.

**세 결정(확정):**
1. **`DISCONNECTED_RESULT` 은퇴 → 다중 솔리드 출력. 불리언이 `Vec<Solid>`를 반환.** "Cut 두 동강"·"엣지 접촉 Fuse"가
   전부 정상 결과. `live_solids: Vec<Handle<Solid>>` 인프라 이미 존재 — 불리언 쪽 제약(양수 셸 ≥2 거절)만 걷는다.
   (구현 접점: `assemble_fuse_cut`의 `positives.len()!=1 → DISCONNECTED_RESULT`를 **전 positive를 각 솔리드로
   방출**로; 성분 부호 분류(design.md §9 5d #5)와 연동. 반환 타입 변경의 blast radius = 모든 boolean 호출부.)
2. **non-manifold 솔리드 미지원 — 그리고 불필요.** OCCT도 안 만든다(엔티티명부터 MANIFOLD). **각 솔리드 안의
   manifold 전제(엣지당 면 2·Euler)는 그대로.** 공유 엣지가 compound 레벨에서 4면인 것은 각 솔리드가 2면씩이므로
   위반이 아니다. validate·Euler·불리언 구조를 안 건드린다(단, validate가 **per-solid**인지 이식 시 확인 — 전역
   엣지-면 카운트면 공유 경계에서 오탐 가능, 그때만 per-solid로 조정).
3. **솔리드 간 경계 요소 공유가 필수 요건.** OCCT가 접촉 엣지를 공유한다(E24→23·V16→14). nacre `Vec<Solid>`도
   솔리드들이 정점·엣지·면 Handle을 공유할 수 있어야 하고, 이는 §5 명시 공유(H3)와 같은 메커니즘이다 — OCCT는 그
   공유를 **불리언이 명시적으로 만든다**(전역 자동병합 아님). **즉 OCCT가 §5의 명시 공유를 독립 확증한다.**

**★ 교정(과거 오판):** 오버홀 논의 중 "요소 공유가 non-manifold를 부른다"는 우려가 있었으나 **반증됐다** —
manifold는 솔리드별 판정이며, 두 솔리드가 경계 요소를 공유해도 각각은 manifold다. 공유는 문제가 아니라 오히려
불리언이 "여기서 만난다"를 계산 없이 알게 해준다(참조-공면의 확장). (design.md §9에도 기록.)

- **살림**: 일반 seam 경로, exact 술어(`nacre-predicates`), (5d) 정밀도 인프라, `Store`/`Handle`, extrude+boolean
  pad/pocket.
- **교체**: 명시 공유가 흔한 공면을 **공유 토폴로지**로 만들어, 기하 공면 사이드카(detect_*_contact 등 6 감지기)의

  그 케이스를 커버함을 **코드로 실증한 뒤**(회귀 0)에만, 사이드카를 신뢰 fallback으로 두고.
- **단계 순서**: 2D 실험(선검증) ✅ → design/overhaul 확정 ✅ → (5d) #4·#5 마무리 ✅(#4 fan zero-area·#5 cavity

- **이식 진행 (overhaul 브랜치).** main의 (5d) 완료를 병합한 뒤 3D 이식을 셀 단위로 진행한다.
  - **#1 ✅ 유리수 스칼라 토대** — 새 `nacre-scalar` 크레이트에 검증된 `Rat`+`Angle` 이식(§4 exact 값 엔진,

## 10. 비목표

- **곡면**(M6+): 이 오버홀은 여전히 평면 솔리드(다면체).
- **파라메트릭 편집**(로그 중간 파라미터 수정): v1 비목표(§0-3, TNP). 단 provenance 타입은 편집 확장 가능한 형태로.

  Handle 재사용으로 추이성 붕괴를 구조적으로 차단.

**★ 2D 실험의 한계(정직 — 과신 금지).** 선검증하는 2D 실험은 **토대**(유리수·각도·exact 일치·TIP 필터·op-log
시너지)만 검증한다. **3D-특유는 못 본다** — 3-평면 implicit point(2D는 2-선 교차라 근본적으로 더 단순), boolean이
공유-토폴로지 피연산자를 받는 3D 구현 형태, 다중 솔리드 방출·경계 공유의 3D 재구성(정책은 §8로 확정, **구현**은
이식 단계). 2D go/no-go는 **토대에 대한** 판정이고, 3D-특유 위험은 이식 단계(또는 후속 실험)에 남는다. 이것들은
§11(B)로 분리해 둔다.

### (B) 3D 이식 단계에서 정함 (2D 실험 밖)

2D는 **토대**(유리수·각도·exact 일치·TIP 필터·op-log 시너지)를 검증하지만 **3D-특유는 못 본다**(§10 "2D 실험의
한계"). 아래는 2D findings가 판정할 수 없고 이식 단계에서 정하거나 확인해야 한다.

6. **boolean이 토폴로지-공유 피연산자를 받는 3D 구현 형태.** 공유 = 미리 만든 seam vs 프레시+dedup. 2D는 2-선
   교차라 근본적으로 더 단순하고, 3D는 **3-평면 implicit point**·다중 솔리드 방출·경계 공유의 재구성이 붙는다 —
   2D 실험은 이 형태를 판정할 수 없다.
8. **★ validate가 per-solid인가 전역인가.** §8 결정 2의 단서: 다중 솔리드가 경계 엣지를 **공유**하면 **전역**
   엣지-면 카운트는 그 엣지를 "면 4개"로 보아 **정상 형상을 non-manifold로 오탐**한다(각 솔리드는 2면씩이라 위반
   아님). **이식 전에 확인하고 필요시 per-solid로 조정**해야 한다. 2D는 이 다중-솔리드 경계 공유 구조가 없어 실험이
   드러내지 못한다.
9. **★ declare-0 확인 요청의 실무 발생 빈도(사용자 방해도).** §6 정책은 declare-0 조건에서 사용자에게 확인받는데,
   "실제 CAD 모델링 패턴에서 얼마나 자주 물어보게 되는가"는 2D 샌드박스가 재현 못 한다(2D는 무작위 회전 통계까지만 —
   §11-A 7-ii). 너무 잦으면 방해가 되므로, 실무 발생률은 3D 이식·실사용 후 실측한다. **비인터랙티브(스크립트) 모드는
   기본 `Reject`**라 발동 시 에러로 정책 명시를 요구(§6) — 이 경우 발생 빈도가 곧 "명시가 필요한 빈도"다.
10. **★ `Separate` 옵션의 실무 실현 빈도.** 1e-30 떨어진 두 점을 별개로 두면 1e-30 두께 슬리버가 생겨 병합-전-검증의
    "퇴화 엣지/면 없음"에서 거의 항상 탈락한다(§6 잔여 c). 따라서 `Separate`가 실제로 유효하게 실현되는 경우가 얼마나
    되는지는 실무 형상에서만 보이며, 2D·인위적 재현으로는 대표성이 없다.

실험 findings가 (A)를 판정하며 이 문서를 갱신한다(가정 → 검증된 결정). 실험은 별도 `experiment/exact-2d` 브랜치의
격리된 2D 샌드박스에서 협업·반복으로 진행한다. (B)는 3D 이식 플랜에서 다룬다.
